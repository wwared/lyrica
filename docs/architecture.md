# Architecture

```
iPhone (PWA) ──HTTPS/WSS── Caddy ──HTTP/WS── lyrica (crates/lyrica) ──TCP── MPD
                                               │  embeds web/ build
                                               └─ uses lyrica-mpd (crates/mpd)
```

Measurements backing the design: "Queue measurements" (MPD and server, under "MPD bridge") and "Measurements" (frontend, at the end).

## `lyrica-mpd` (crates/mpd)

Async MPD client library, independent of the web server: tokio TCP, responses parsed with nom 8 (`Parser` trait API).

- **Commands:** `password`, `status`, `currentsong`, `playlistinfo START:END`, `playlistsearch FILTER window START:END`, `play`, `playid`, `pause`, `previous`, `next`, `random`, `repeat`, `single`, `setvol`, `seekcur`, `listplaylists`, `clear`, `load`, `idle`, command lists. No binary responses.
- **`Client`:** one connection, one command at a time; each response line parsed as `OK`, `ACK …` or `key: value`. `Status` and `Song` keep only the fields lyrica uses, ignoring unknown keys; a multi-value tag keeps its first value; `playlistinfo` starts a new `Song` at each `file` line. `Track` is the first `Track` line as a number, `None` when it isn't one, so an odd tag never fails a window.
  - **Errors:** an `ACK` leaves the connection usable. I/O and protocol errors, or a command future dropped mid-response, leave it out of sync: later commands fail with `Error::Broken`. The library doesn't reconnect; the caller does, also after MPD's `connection_timeout` (default 60 s unused) closed it.
  - **Reads:** `TCP_NODELAY` is set and `TCP_QUICKACK` re-armed before every read (Linux, `socket2`; see "Socket options"). Lines go into their own buffer before joining the response: tokio's `read_line` re-validates its whole buffer's UTF-8 on each call, quadratic over a long response.
  - `idle` blocks its connection, so it needs its own `Client`. Arguments are always quoted; newlines are rejected.
  - **Queue ranges** (`queue_range`): MPD clamps the end to the queue length and returns nothing for an empty range; a start past the end, or after the range's end, is an `ACK`.
  - **Command lists** (private): `replace_queue` (`clear` + `load`), `play_in_order` (`random 0` + `single 0`, then `playid` when given an id) and `search_queue`. One write, answered by one `OK` or the failing command's `ACK`, whose index says which. Not transactions: earlier commands stay done (a gone id: `ACK [50@2] {playid} No such song`, both modes off). `playid` of the paused current song plays it from 0:00.
  - **Queue search** (`search_queue(filter, window)`): `status` + `playlistsearch FILTER window START:END` in one command list, so the queue version and length belong to the matches; returns those and the matches' positions only. `window` counts matches; MPD clamps its end and rejects a start past the queue's length (`Bad song index`) or an end over 2³¹ − 1. The response is split at its first `file` line, as status and songs share keys (`duration`). `Filter` (regex, `Not`, `And` over six tags) renders MPD's filter syntax, patterns verbatim in single quotes with `\` and `'` backslashed; argument quoting adds the second level. An empty `And` has no MPD form: `Error::InvalidArgument`, nothing sent.
  - **Stored playlists:** `playlists` (`listplaylists`, MPD's order) and `replace_queue`; nothing edits them.
- **Connection multiplexing:** slow work must never delay interactive work. The server uses one connection idling for state changes, one for commands, and one for queue windows, playlist listings and searches (see "MPD bridge").
- **Ranges, never wholesale:** MPD serves every client from one event loop, so a large response delays all connections. Queue windows stay around 100 entries, under 1 ms of MPD time (see "Queue measurements").

## Server (crates/lyrica)

Thin bridge between the frontend and `lyrica-mpd`: axum on tokio, serving the embedded frontend (rust-embed) and its WebSocket at `ws`, relative to the page. Plain HTTP behind a TLS-terminating reverse proxy (Caddy); frontend URLs are relative, so a path prefix works if the page URL ends in `/`. Configuration is CLI arguments (clap) plus `LYRICA_MPD_PASSWORD`; no disk state.

Album art and MPD's `httpd` stream go straight from their source to the browser (no server hop or bandwidth, browser caching): the server only supplies the song's folder URL on an HTTP mirror of the music library (art is only looked for in that folder) and `--stream-url`.

### MPD bridge (`bridge.rs`, `ws.rs`)

- **CLI:** `--listen` (default `127.0.0.1:8080`); `--log` (`EnvFilter` syntax, default `info`); `--mpd <host:port>` (TCP only, default `127.0.0.1:6600`); `--mpd-password` or `LYRICA_MPD_PASSWORD` (keeps it out of the process list), sent with `password` after every connect; `--music-url <URL>`, base URL of an HTTP mirror of MPD's music directory (e.g. `https://music.example.com/`; a missing trailing `/` is added), without which `folder` is always `null` and no art shows; `--stream-url <URL>`, MPD's `httpd` output (HTTPS when the page is, or it's blocked as mixed content), without which there is no play-here toggle.
- **Idle connection:** a task fetches `status` + `currentsong`, publishes the snapshot, then loops `idle(player, options, mixer, playlist)` → refetch → publish. Fetches never queue behind commands.
- **Command connection:** a task serves commands and stored playlist loads from all WS clients, in order, from an `mpsc` (capacity 16). On `Io`/`Broken` it reconnects and retries once (a connection MPD closed for `connection_timeout` never ran the command); `Ack` is logged, not retried.
- **Snapshot fan-out:** `tokio::sync::watch`; each WS client gets the current snapshot on connect, then every change. While playing, `elapsed` is advanced to the send time (capped at `duration`).
- **MPD unreachable:** the idle task publishes an `offline` snapshot and reconnects with backoff (1 s doubling to 10 s). Commands sent meanwhile are dropped and logged; loads get an error reply.
- **WS protocol:** JSON text messages (serde); invalid ones are logged and ignored.
  - Server → client, first on every connection: `{"type":"config","stream":string|null}`, `stream` being `--stream-url` verbatim.
  - Server → client: `{"type":"state","state":"play"|"pause"|"stop"|"offline","title":string|null,"artist":string|null,"album":string|null,"folder":string|null,"elapsed":number|null,"duration":number|null,"volume":number|null,"random":bool,"repeat":bool,"single":bool,"queue":{"version":number,"length":number,"position":number|null,"id":number|null}|null}`.
    - `title`: `Title`, else the file name; `null` without a current song. `artist`: the first `Artist`, else the first `AlbumArtist`. `album`: the first `Album`, else the file's folder name (none for streams or files at the top of the music directory). `folder`: `--music-url` plus the song's directory, each segment percent-encoded (RFC 3986 unreserved characters kept), ending in `/`; `null` without `--music-url` or a song, and for streams (`file` containing `://`). All from the `currentsong` already fetched: no extra round trip.
    - `elapsed`/`duration`: fractional seconds from `status` (`duration` falling back to `currentsong`'s). `volume`: 0–100, `null` when MPD reports none (no mixer, or none open); the bridge idles on `mixer`, so other clients' changes are pushed. `random`/`repeat`/`single` from `status` (`false` offline), `single` also `true` for `oneshot`; consume is absent (unused).
    - `queue`: version, length, current position and id (`playlist`, `playlistlength`, `song`, `songid`); `position`/`id` `null` without a current song, `queue` `null` offline. Idling on `playlist` pushes every queue change; entries never travel in `state`.
  - Client → server: `{"type":…}` with `previous`, `toggle`, `next`, `random`, `repeat`, `single`; `{"type":"volume","volume":0–100}` (`setvol`, MPD's global volume; MPD rejects over 100, logged); `{"type":"seek","position":seconds}` (`seekcur`, absolute, millisecond precision; negative or out-of-range is invalid; MPD rejects it while stopped); `{"type":"playid","id":n}` (a window entry's `id`; MPD rejects one gone from the queue, logged); `{"type":"albumstart"}` (see "Queue actions"); window requests (see "Queue"), playlist listings and loads (see "Stored playlists") and searches (see "Search" → "Server").
  - No replies to commands: the state push `idle` triggers is the confirmation. On the local MPD, WS client to state message: `toggle` 0.4–1.8 ms, `next` 19 ms, `previous` 3 ms. A dropped MPD connection shows `offline` within 40 ms; the first command after a lost connection or a 65 s idle gap reconnects and succeeds in < 2 ms. MPD doesn't time out connections in `idle`.
- **Toggles** are mapped from the latest snapshot. `toggle`: `play` → `pause(true)`, `pause` → `pause(false)`, `stop` → `play()`. `random`/`repeat`: the opposite of the current mode. `single`: on (`oneshot` included) → `single 0`, off → `single 1`. Never a command that changes nothing: MPD emits no idle event for it, so clients would get no update.
- **Queue:**
  - **Queue connection:** a third `Client`, owned by a task (`serve_reads`) serving window requests, playlist listings and searches from all WS clients over a bounded `mpsc` (capacity 64), one MPD command at a time; searches a step at a time, waiting requests first (see "Search" → "Server"). Connected on first use, with the command connection's reconnect-and-retry-once helper. State pushes and commands never wait on it, though MPD itself serves no one during a search's scan.
  - **Socket options:** every MPD `Client` re-arms `TCP_QUICKACK` before each read (Linux resets it), avoiding 40 ms stalls (see "Queue measurements"). Over a network a segment holds ~1.4 KB (loopback 64 KB), so even a tag-heavy `currentsong` can span segments; the cost is one `setsockopt` per read. Accepted HTTP / WS connections get `TCP_NODELAY` (`ListenerExt::tap_io`; axum doesn't set it): with Nagle, a state push right after a window reply would wait 40 ms for the proxy's delayed ACK. `TCP_QUICKACK` doesn't help there: it only affects our own ACKs.
  - **Windows:** client → `{"type":"queue","version":n,"start":n,"end":n}` (positions, `end` exclusive; `start` > `end` is invalid). Server → `{"type":"queue","version":n,"start":n,"songs":[…]|null}`, `version` and `start` echoed (`version` unread). Every valid request gets exactly one reply.
    - **Cap:** `end` is clamped to `start + 200` (0.8 ms of MPD time), so nothing requests the whole queue. `songs` may be shorter: clamped, or past the queue's end. `start` = `end` replies `[]` without asking MPD.
    - **Entry before:** for `start` > 0 one `playlistinfo` reads `start − 1 … end` (one queue version), the leading entry only deciding the first entry's `start` flag. The cap counts requested entries; `start` = length reads one entry and replies `[]`.
    - **`[]` vs `null`:** an `ACK` (e.g. `start` past the end after a shrink) replies `[]`, a state push with the new version following. `null` means unserved, retry later: the channel was full, MPD is offline, or it was unreachable after the retry. Requests from a since-closed connection are skipped.
    - **Entries:** `{"id":n|null,"title":s,"artist":s|null,"album":s|null,"track":n|null,"duration":n|null,"folder":s|null,"start":bool}`, positions implied (`id` is MPD's `Id`, `null` only if MPD sends none); the state message's fallbacks, from the same helpers. `start`: whether it starts an album group (see "Album grouping"). MPD sends every tag (300–1,100 B per entry); the server forwards a fraction.
  - **Consistency without locking:** the client tags each request with its queue version and drops replies for an older one. A window read just before a change's state push is stored under the old version and dropped when the push lands: at worst a refetch, never stale rows shown as current.
  - **The WS loop never waits on the queue:** requests go out with `try_send` (full: an immediate `null`), carrying the connection's unbounded reply sender (bounded in practice by the request channel), so the queue task never waits on a slow client either. The loop's `biased` `select!` takes state changes, then replies, then incoming messages, so a reply never delays a push. Replies are small (≤ 200 entries, tens of KB).
- **Stored playlists** (frontend: "Stored playlists" under "Frontend"):
  - **Listing:** `{"type":"playlists"}` → `{"type":"playlists","names":[…]|null}`, to that client. Served like a window; names sorted case-insensitively by code point (ties: upper case first). `null`: channel full, MPD offline (not asked), or MPD failed (`ACK`, or unreachable after the retry).
  - **Loading:** `{"type":"load","name":s}` → `{"type":"loaded","name":s,"error":s|null}`, to that client once MPD answers. On the command connection, in order with commands (one channel of `Job::Command` / `Job::Load`): `listplaylists`, then `replace_queue` only if the name is listed, in one call of the retry helper (a retried `clear` + `load` is harmless). Errors: `"MPD offline"` (not asked), `"Busy"` (command channel full, refused at once via `try_reserve`, so the WS loop never waits to queue a load), `"No such playlist"` (queue untouched), MPD's `ACK` message (e.g. `"Playlist is too large"`), or the connection error.
  - **During a load** MPD serves no one: every client's state fetches, windows, listings and commands wait. Once the command channel (16) is full, a WS loop sending one more waits too, holding back that client's pushes, which MPD isn't producing anyway.
- **Queue actions** (frontend: "Queue actions" under "Frontend"):
  - **Album start:** `{"type":"albumstart"}` turns random and single off and plays the current song's album group in order from its first entry; repeat untouched. A command like the others: command connection, in order (a `next` sent just before is seen), dropped offline, confirmed by the state push. It runs inside one call of the retry helper, so a retry reruns it whole, fresh `status` included. No current song: nothing. Otherwise the walk finds the group's first entry, then `play_in_order` sends `random 0`, `single 0` and `playid` with that entry's id, which plays it from 0:00, also when it's the current song paused or stopped. Only when the first entry is the current song and playing is `playid` left out, so it carries on. The modes are sent even when already off, unlike the toggles' rule: the frontend re-centres on its own rather than waiting for a push.
  - **The walk** (`group_start`): `playlistinfo` backwards in windows of 100, the first ending at the current song; entries converted like a window's (`Entry::new`, which is why the command task gets `--music-url`: `folder` is part of the rule) and compared with `same_group`, across window edges too, stopping at the first entry outside the group or at position 0. Usually one window; no cap: a group spanning a whole ~180k-entry queue would take ~1,800 windows, ~0.8 s, with other connections served between them.
  - **Races:** a queue change between `status` and the reads may `ACK` (logged) or pick another group; `playid` is by id, so it never plays an entry that left the queue.
- **Queue measurements** (local MPD 0.24, ~180k-entry queue):
  - **Windows:** raw `playlistinfo` of 100 entries 0.4–0.7 ms and 31–114 KB, of 1,000 entries 4.5 ms / ~650 KB, the whole queue ~130 MB in 10.7 s; `status` 0.09 ms. Through `lyrica-mpd` (release build): medians 0.07 / 0.13 / 0.23 / 0.43 / 0.82 ms for 10 / 25 / 50 / 100 / 200 entries, max 1.3 ms; `status` and `currentsong` 0.02–0.03 ms. Without `TCP_QUICKACK`, up to 39 of 40 windows of 25–100 entries took 41–42 ms, `TCP_NODELAY` or not: MPD holds a response's last segment until our ACK arrives, which Linux delays by 40 ms. Single-segment responses never stall.
  - **Over the WS** (release build): 0.29 ms for 3 entries, 0.81 ms for 200 (30 KB). Under a client fetching random 100-entry windows back to back (~2000/s), lyrica's time from MPD's `idle` event to the DOM goes from 0.44 to 1.41 ms median for pause / play and from 0.82 to 1.93 ms for `next`, mostly MPD answering the idle connection between reads. Windows stall only while MPD opens the next file (max 155 ms).
  - **Loading stored playlists** (throwaway MPD 0.24.15, release build): 1,000 / ~20k / ~200k songs in 1–9 / 10–17 / 83–105 ms (`loaded` over the WS after 1.1 / 10.8 / 107 ms); listing 7 playlists 0.6 ms (`listplaylists` 0.05 ms median on the real MPD). MPD answers no one meanwhile. Other clients get one `playlist` event (one state push) per load, `status` already showing the new length: no empty queue in between, though the version moves by 2. Per-song cost is MPD's database lookup, growing with directory width: ~200k songs over 4,000 sibling directories take 2.5–2.7 s. On the real MPD `playlistlength` takes 1.9 / 17.4 / 19.2 s for ~20k / ~180k / ~200k-song playlists, freezing MPD likewise, so loading them is estimated to take as long.
  - **Failed loads:** a missing name → `ACK [50@1] {load} No such playlist`, queue left empty (lyrica's name check answers in 0.3 ms, queue untouched); over `max_playlist_length` → `ACK [51@1] {load} Playlist is too large`, queue filled up to the limit; missing files are skipped without an error.
  - **Queue search** (`playlistsearch`, MPD 0.24.0, whole scans unless noted):
    - **Filters:** regex (`=~`) on title, artist, album and file 59–63 ms against `contains`' 610–650, `any` 126 against 1,640, with the same matches except non-ASCII case and ß. `(*UTF)` adds 15 ms. The five default fields 88 ms, 77 with file first. `(*UCP)` costs up to 1.5× for repeated classes (`\w+ö\w*` 101 → 145 ms, `love` 78 → 87). A negated term first costs 140 ms (nearly every entry passes it), three 263; a rare word first, 82.
    - **Windows:** `window 0:5` of a common term 1.2 ms (the scan stops once the window is full); `window k:k+1` costs the scan up to the k-th match, a full scan (~60 ms) when there is none. A start past the queue's length: `Bad song index` (0.1 ms); an end over 2³¹ − 1: `Number too large`; start > end: `Malformed range`; `k:k` is empty. No position filters (`Unknown filter type: pos`). Unwindowed, title `a` (~110k matches): 5.2 s, ~80 MB.
    - **Chunks** (`search_queue`, release build, one word over the default fields): "love" (~3k matches) `0:500` / `500:1000` / `1000:1500` / `1500:2000` 11.9 / 25.5 / 48.8 / 61.4 ms, probes past the last match 79–81 ms; "the" 2.3–3.7 ms per chunk; no match 78–80 ms per window. Picking the positions out of the full tags: ≤ 0.3 ms. Two words cost one (`river night` 79.7 ms): the second term only runs on the first's matches.
    - **Query costs per step** (MPD time): one negated term is cheap, as chunk reads stop at the 500th match (`-live`: first match 5 ms from `null`, 149–227 ms from 90,000; total in 0.3–0.5 s; steps ≤ 84 ms). Several negated terms on rare words pass nearly every entry through every regex: last-chunk count reads 136–150 ms for two (`-live -demo`), 190–200 ms for three (`-live -demo -remix`: 8 steps, 1.3 s), nothing extra after a rare positive term (`love -zzqx -qxzz -xzqz` ≤ 90 ms). `any:` steps 105–150 ms (`any:love` total 0.4–0.6 s, `any:x` ~1 s over 11 steps). Regexes cost like words (`/é\b/` ≤ 85 ms, `file:/\.flac$/` ≤ 37).
    - **Correctness** (over the WS): the example table and ~20 more queries matched a client-side evaluation and the matches' tags; `MÖBEL` / `möbel` and `Σ` / `σ` find the same entries.
    - **Server search** (release build, over the WS):
      - **First match** (request to final reply): "love" from 0 or `null` 17–18 ms (chunk 0 only), from 30,000 49 ms (2 chunks), from 90,000 141 ms (3), from 170,000 106 ms (2); "the" (~50k matches) from 100,000 158 ms (5); "a" (~170k) from 150,000 117 ms (5); no match 84 ms. Chunk 0 goes out within 2–18 ms for common words.

      - **Others while searching** (searches back to back, MPD scanning nearly all the time; another client fetching random 100-entry windows every 20 ms; a third toggling pause): windows median 20 ms, max 86–92, no `null` (0.8 / 3 without searches); state pushes median 34–42 ms, max 55–60 (0.3 / 0.6). ## Search

Finds matches in the live queue with MPD's `playlistsearch` and centres the list on them one at a time, without playing them. Measurements: "Queue measurements" → "Queue search" and "Measurements" → "Search mode".

### Behaviour

`search-mode.tsx`, `search.ts`.

- **Button:** `search`, the toolbar's second, disabled offline; entering closes the volume pill.
- **Search mode:** the toolbar becomes `[✕][input ⌫][🔍]` (a `role="search"` form), its other buttons (the playlists button and dialogs included) unmounted, the input focused: `type="search"`, 16 px (iOS zooms in on smaller), `user-select: text`, `enterkeyhint="search"`, autocorrect (an attribute: Preact would set the `autocorrect` property to `true` from `"off"`), autocomplete, autocapitalize and spellcheck off. ⌫ replaces the native clear button: Material's `backspace` (distinct from ✕, which leaves), 20 px, muted, over the input's right end while it holds text, a 44 px target; it empties and focuses the field, keeping an open keyboard (no focus change on `mousedown`); matches stay until the next submit.
- **Submit:** Return or 🔍 blurs (closing the keyboard) and runs the query; a blank one does nothing. The query stays, editable. Every submission, the same query included, replaces the matches, like leaving and re-entering.
- **Pill:** while a search is pending or has a focused match, `( ▲  3 / 120  ▼ )` centred 10 px above the list's bottom edge: 44 px buttons, the count in a fixed 8rem box (tabular digits) so the buttons never move, a `bg0_s` pill bordered like the volume pill. ▲ previous, ▼ next, wrapping. While pending, the "Loading…" spinner replaces the count and ▲▼ do nothing. The total reads `…` until known: from a chunk under 500 matches (its start plus its count), an empty chunk after a full one, or `total` (a fraction of a second after the first match). Until then ▲ on the first match is disabled: wrapping back needs the last match.
- **Room for the pill:** in search mode the list ends in 64 px of empty space, so the last row, scrolled to or centred, rests 8 px above the pill.
- **First match:** the first after the current song, wrapping to the queue's first; from the top without a current song.
- **Focused match:** centred instantly like auto-centring, halting a fling the same way; never played. Matches among held chunks get `bg1` and a 4 px yellow left edge (`bg1` alone is too close to the `bg0_s` stripes), muted text `fg3` (`fg4` on `bg1` is 4.2:1, `fg3` 5.3:1; the current song's orange 4.6:1); the focused one `bg2` with the edge and yellow text (5.2:1), like the playlists dialog's selection, over the current song's orange.
- **Auto-centring** is held throughout: song changes move the highlight, not the list, and the resume timer doesn't centre. Scrolling is free; ▲▼ continue from the focused match. A row tap plays it and search mode stays; the current song's row does nothing. A cover tap still centres the current song.
- **Stale matches:** another version in a state push, `searchstale`, a chunk fetch answered for another version, or a closed socket make the positions stale: the next ▲▼ reruns the query from the focused match's position in its direction. The old matches stay highlighted until the rerun's first reply.
- **Errors and no matches:** a toast: the server's error ("Empty search", `Missing closing "`, `Missing closing /`, MPD's error such as an invalid regex, "MPD offline", "Busy"), "Not connected" (closed when sending), "Connection lost" (closed while pending), "Couldn't load matches" (a chunk fetch unserved), "No matches". Search mode stays.
- **Leaving:** ✕, Escape (desktop; in the input it would otherwise clear the field) or switching to full mode clears the query, restores the toolbar, sends `searchend` and resumes auto-centring, centring the current song like a cover tap; the switch to full mode hides the list first, leaving the centring to the next opening. Nothing persists.

### Query language

`query.rs`: nom parses a query into terms, `compile` turns them into a `lyrica_mpd::Filter`. Case-insensitive throughout, field names included; only a regex can opt out, with `(?-i)`.

```
query = term (spaces term)*
term  = ["-"] [field ":"] value
value = "^" atom | atom | "/" regex "/"
atom  = word | '"' text '"'
field = title | artist | albumartist | album | file | any
```

- **Terms** are joined by AND. A term matches when one of its fields does: its field, or the default fields `file`, `title`, `artist`, `albumartist`, `album` (never `any`). Different terms may match in different fields.
- **Word:** substring (`love` finds "Glove"). **Quoted:** substring including spaces; `\"` and `\\` inside. **`^`:** starts with. **`/re/`:** MPD's PCRE2 regex under a match limit, with Unicode `\w`, `\d`, `\s` and `\b` (see "MPD filters" → "User regexes"), `\/` for `/`, other backslashes passed on.
- **Regex tips:** MPD's regexes ignore case, so `(?-i)` at a regex's start makes it case-sensitive (`/(?-i)LOVE/` finds "LOVE", not "Love"; `(?-i)` mid-pattern from there on, `(?-i:…)` for a group only). Plain groups don't capture: for a backreference name the group (`(?<c>\w)\k<c>`) or start with `(?-n)`.
- **`-`** negates any whole term: none of its fields matches. Only in front: inside a value it is literal (`artist:-live` contains "-live").
- **Plain text** where nothing else applies: an unknown prefix (`vol:2`), a lone `-` or `^`, `^/x/` (starts with "/x/"), a field with nothing after it (`artist:` then a space or the end), a `"` or `/` not starting a value (`rock/pop`, `foo"bar`).
- **Spaces:** Unicode whitespace (`char::is_whitespace`; nom's `multispace` is ASCII only). A word runs to the next space.
- **Delimited values** end at their closing delimiter, which also ends the term: text right after it starts the next term (`"a"b` is `"a" b`; `/x/i` is `/x/` and `i`, MPD's regexes being caseless already). Quoted text: `\"` is `"`, `\\` is `\`, other backslashes literal. Regex: `\/` is `/`, any other backslash pair passed on whole (`/a\\/` is the regex `a\\`, closed by the last `/`).
- **Empty values** (`""`, `^""`, `//`, negated or not) are dropped: they match everything or nothing. A query of only those is "Empty search".
- **Errors:** an unclosed `"` or `/` (a lone one included), `QueryError` variants with the toasts `Missing closing "` and `Missing closing /`, answered as `searchfailed` like "Empty search". MPD's error for an invalid regex is shown as is, deliberately: its offset counts the pattern sent, our 32-character prefix included (`/(/`: "Error in regex at offset 33").

| Query                         | Matches entries where                                                               |
| ----------------------------- | ----------------------------------------------------------------------------------- |
| `river night`                 | a default field contains "river" and one (maybe another) contains "night"           |
| `"slow river"`                | a default field contains "slow river"                                               |
| `-live ^hello /world wide/`   | no default field contains "live", one starts with "hello", one matches `world wide` |
| `artist:someband -album:live` | the artist contains "someband" and the album doesn't contain "live"                 |
| `-^the`                       | no default field starts with "the"                                                  |
| `file:/\.flac$/`              | the path ends in ".flac"                                                            |
| `/(?-i)LOVE/`                 | a default field contains "LOVE" in capitals                                         |
| `vol:2`                       | a default field contains "vol:2"                                                    |

### MPD filters

- **Regex only** (`=~`, negated `!~`): 10× faster than `contains`. Words and quoted text compile to escaped `(*UTF)` literals (every ASCII non-alphanumeric character backslashed), `^` prefixing `^`; regex syntax only inside `/…/`.
- **`(*UTF)`** starts every regex, the user's too: MPD compiles regexes in byte mode, where case folding is ASCII only and `.` is a byte; `(*UTF)` switches PCRE2 to UTF-8 with Unicode case folding (ö/Ö, σ/ς/Σ). Not covered: multi-character folding (ß ≠ ss), accents (mobel ≠ möbel, as with `contains`), accents stored as combining marks (a typed "atún" misses them).
- **Several fields** (MPD 0.24 has no `OR`): `(!((file !~ 'r') AND (title !~ 'r') AND …))`; negated `((file !~ 'r') AND …)`; one field `(f =~ 'r')` or `(f !~ 'r')`. Default fields file first (77 ms against 88).
- **Order:** `AND` stops at the first false operand, so positive literal terms (words, quoted, `^`) go first, longest first (likely the most selective; characters, ties in query order), then positive regexes, then negated terms, both in query order.
- **Negation is per song:** `(any !~ r)` holds when no tag matches (`((any =~ x) AND (any !~ x))` is empty for `a`, `the`, `love`, though every entry has several tags). Named tags go through the same MPD filter, so multi-valued ones negate the same way: `-any:x` and multi-valued tags need nothing special.
- **User regexes** get `(*UTF)(*UCP)(*LIMIT_MATCH=10000)` in front and nothing else checked: safety and responsiveness over completeness. `(*UCP)` gives Unicode `\w`, `\d`, `\s`, `\b` and POSIX classes, ASCII otherwise (`é\b` matches about three times as many titles without it). MPD compiles caseless and without auto capture, hence `(?-i)` and named groups or `(?-n)` (`(\w)\1` is "reference to non-existent subpattern"); `(?x)`, atomic groups, possessive quantifiers and `(*COMMIT)` work. A user's own `(*…)` verbs pass through untouched, deliberately: they stay valid right after ours (anywhere else a verb is an error), and a `(*LIMIT_MATCH=n)` overrides ours (PCRE2 takes the last), lifting or lowering the limit. MPD reports an invalid regex (`searchfailed`).
  - **Why a limit:** a running scan can't be cancelled: MPD runs commands on its main thread, and closing the socket (reset or half-close) changes nothing (`^…(a*)*$` against 28 `a`s and a `b` over 2,000 entries: ~15 s, every other connection waiting). Everyday regexes (`love.*heart`, `(love|heart).*(night|dream)`, `\b(live|demo)\b`, `^(?!.*live).*love`, `(.*a){5}`, …) cost 0.002–0.004 ms per entry, like a word; only a repeated group whose content repeats too, splitting the same text many ways, is slow: `(.*)*remix`, `(\w+\s?)+$`, `(\w+\s*)+[!?]` cost 5–14 ms per 135-character entry unlimited (~15–40 min over a ~180k-entry queue), 0.009–0.024 ms under the limit.
  - **Its cost:** MPD counts a limit hit as no match, so such a regex misses entries silently: of ~700 entries containing "remix", `(.*)*remix` finds none, `(\w+\s?)+remix` ~140, and negated, `-/(\w+\s?)+remix/` keeps ~860 entries against the ~300 without "remix". Over the real queue 65 plausible regexes (anchors, classes, Unicode properties, `.*` chains, alternations of up to 20 names, lookarounds, path shapes) lose nothing at 10,000, except the "at least n of" idiom (`(.*e){7}` loses a few entries, `(.*e){8}` over a thousand, `(.*\s){10}` thousands; all fine at 100,000).
  - **Its reach:** the limit is per start position, not per entry: against a file name of over 200 characters, `(a?){n}a{n}[bz][bz]` tuned to stay just under it at each start costs up to 1.2 ms per entry (~4 min over 200,000 entries for that one field). Such tuning doesn't happen by accident.
- **Quoting, two levels:** the value in single quotes inside the filter, the filter in double quotes as the command's argument; each level backslash-escapes `\` and its quote, so a regex backslash is four on the wire. An apostrophe in a word: `\'` in the regex, `\\\'` in the filter, `\\\\\\'` on the wire (four backslashes would end the value early). Quoted keywords (`"window"`) and a lone operand in parentheses (`((title =~ 'x'))`) are accepted.

### Server

- **`lyrica-mpd`:** `search_queue` (see "`lyrica-mpd`" → "Queue search"): `status` first in the same command list, so the queue version belongs to the result (MPD serves no one else during a list); only the positions are kept.
- **Messages** (`ws.rs`, `search.rs`):
  - Client → `{"type":"search","id":n,"query":s,"from":p|null}` starts a search, replacing the connection's previous one; `from` is the current song's position. The WS loop compiles the query, so a query error is answered at once, without the queue task.
  - Server → `{"type":"matches","id","version","start":k,"positions":[…]|null,"first":i|null}`, a chunk: matches k to k + 499 in queue order, k a multiple of 500, fewer meaning the last; `version` the queue's when found. A search sends every chunk it reads, chunk 0 first, at once; the last reply carries `first`, the index of the first match after `from` (0 when none follows it, or no `from`), and is the chunk holding it, sent again if it went out earlier (chunk 0 when wrapping). Chunk 0 empty (`[]`, `first` `null`) means no matches; a later empty chunk is a probe past the last match.
  - Client → `{"type":"matches","id","query","start":k}` fetches another chunk: one MPD command served like a window, independent of the running search. `positions` (and `version`) `null` when unserved (channel full, offline, MPD unreachable), `[]` on an `ACK` (the queue changed; its state push follows).
  - Server → `{"type":"searchfailed","id","error":s}`: the query error, MPD's `ACK` message on chunk 0 (e.g. an invalid regex), `"MPD offline"`, `"Busy"` (queue channel full) or the connection error. `{"type":"searchstale","id"}`: the queue's version changed between steps, or a later step got an `ACK` (`Bad song index` after a shrink; chunk 0 ran the same query); the client reruns at once if its search is pending, else on the next ▲▼. `{"type":"total","id","version","total":n}` once counted, after the reply with `first` (with it when chunk 0 is short); only `total`, not the chunks the count reads, so a `matches` reply after `first` is always a chunk fetch's. No matches: no `total`.
  - Client → `{"type":"searchend"}` drops its search. Dropped itself when the channel is full: the search then ends on its own, its replies ignored by id.
- **Scheduling:** searches run in the queue task (`serve_reads`), one MPD command per step; before each step, waiting windows, listings and chunk fetches go first (`try_recv`), so they wait at most one step. Searches of several connections take turns (round robin), one per connection, keyed by its reply channel; a new search, `searchend` or a closed socket drops it. Consecutive steps are 2 ms apart (`STEP_GAP`): a state change during a scan sets off the idle connection's `status` and `currentsong` once MPD is free, and without the gap the next scan would get there first, so pushes would wait out two scans (max 104 ms against 55–60). Counting is background work: its steps wait until 100 ms (`COUNT_IDLE`) after both the first match was sent and the task's last request, the task sleeping until then or the next request. So the rows loaded around the revealed match fill 24–32 ms after its reply instead of 62–109 ms behind count reads (whole scans), and while the client keeps requesting windows (scrolling), the count waits.
- **First match** (`Bracket` in `search.rs`): chunk 0 (`window 0:500`) first; done if it has fewer than 500 matches, `from` is `null` or its last position is after `from`. Otherwise later chunks are read whole: a probe costs MPD the scan up to its last match, so 500 matches cost little more than one (tags of 500 matches ~1–2 ms) and the chunk found needs no fetch of its own. The bracket holds `lo`, the last chunk read with all matches at or before `from`, and `hi`, a chunk starting past the first match after it: read with all matches after `from`, empty, or not read but bound by `lo` (positions grow by at least 1 per match, so a match `from − position(last of lo)` indices past `lo`'s end lies after `from`, and one `length − 1 − position` past it can't exist). The next chunk is interpolated: between `lo`'s last and `hi`'s first match when `hi` was read, else with the density up to `lo`; bisected instead after a read that didn't halve `hi − lo`, which bounds the reads to 2⌈log₂(hi − lo)⌉ + 1. A chunk straddling `from` gives `first`; at `hi = lo + 1`, `first` is `hi`'s first match, or, `hi` empty, 0 with chunk 0 resent; a partial chunk all at or before `from` wraps too.
- **Count** (`Count` in `search.rs`): after the reply with `first`, the same search goes on, one chunk read per step, until the last chunk is found: the one with fewer than 500 matches, or a full one with the empty one right after it; then `total`, and the search ends. Finding it is a first-match search with `from = length − 1`, after which no match can follow: a `Bracket` with that `from` from chunk 0 (full; otherwise the total is chunk 0's length, sent at once), fed every chunk read at the search's version, probing's included, so it starts from what probing learnt (a chunk at or below its `lo` or past its `hi` tells nothing new). Full chunks raise `lo`, empty ones lower `hi`, both by the first match's interpolation and bisection with its read bound; it is done at a short chunk (its start plus its length) or at `hi = lo + 1` with `hi` empty (`hi`'s start), which also covers totals known before any count read. A version change or a later `ACK` while counting: `searchstale`.
- **Limits:** target ≤ 65 ms of MPD time per command, ceiling 100 ms. A one-word default-field scan takes 77–85 ms, over the target, and so does every read of the last, partial chunk and every probe past the last match. Over the ceiling, tried on the phone and kept as acceptable: `any:` terms (105–150 ms per step) and two or more negated terms without a rarer positive one (136–200 ms per count read).

### Frontend

- **`ws.ts`:** `connect(…, onSearch)`; `Connection.search(request)` sends `search`, `matches` (a chunk fetch) or `searchend`, `false` unless the socket is open; `matches`, `searchfailed`, `searchstale` and `total` go to `onSearch`, and every close (the visibility reconnect included) hands it `{"type":"lost"}`.
- **`search.ts`** (Vitest): the protocol types and the search state as pure transitions: id, query, version, chunks (start → positions), total, focused index and position, pending (a search with its `from` and direction, or a fetch with its target), stale, and whether the held chunks predate a pending rerun. `submit`, `step`, `reply`, `queued` (each snapshot's version) and `leave` return the next state plus the request to send, a toast and a position to reveal. Ids are a counter in the state; replies to another id are dropped, as are `matches` and `searchfailed` with nothing pending. Also the count text, `canGoBack` and `view`, the rows' questions: whether a position is a held match (binary search in the chunk spanning it) and the focused position.
  - **▲▼ to an unheld chunk** fetches it, spinner meanwhile. `[]` at the same version for ▼: past the last match, the total its start, wrap to 0 (chunk 0 is always held). Another version (`[]` from an `ACK` carries `null`), or `[]` for ▲: rerun at once in that direction. `null` (unserved): a toast, focus unchanged.
  - **Reruns:** ▼ with `from` = the focused position, focusing `first`; ▲ with `from` = the focused position − 1 (`null` at 0), focusing `first − 1`, or with `first` 0 the last match if the total is known, else match 0. `searchstale` while a search is pending reruns it at once, a submission's `from` from the latest snapshot. A finished search is stale when its version differs from the latest snapshot's (a push may land between its last read and its reply).
  - **Replies:** every chunk of the current id is kept; the reply with `first` focuses it and ends pending; chunk 0 empty ends it with "No matches"; `searchfailed` shows its error (a rerun's failure keeps the old matches, stale).
  - **Count:** `total` for the current id and the held chunks' version sets the total, also during a fetch (`…` becomes it, ▲ on the first match wraps); another version, or chunks predating a pending rerun, drop it. A known total survives later chunks (fetches only infer it when unknown); a rerun's replies start over. `searchstale` with a fetch or nothing pending (a count interrupted) marks the matches stale.
- **`search-mode.tsx`:** `useSearchMode` applies the transitions in one object for the app's lifetime, so the socket's callbacks hold it: it sends requests (a refused send answered as `searchfailed` "Not connected"), shows toasts, passes `view` to the list when the chunks or the focus change, and reveals; `App` re-renders on each change. `SearchBar` and `SearchPill` render the toolbar and the pill. `App` holds the toast (shared with `playlists.tsx` through a `toast` callback), renders the search bar or the toolbar's buttons and the pill in the queue area, and leaves search mode in the layout effect that hides the list.
- **Store / list:** the list is memoized on the queue length, so search reaches it through `QueueStore`, like song changes: `store.search(view | null)` enters, updates or leaves search mode (`store.searching`); `store.reveal(position)` centres a row. The listener's `searched(left)` re-renders in the next animation frame, or on leaving recentres like a cover tap (only re-renders while hidden); `reveal` centres at once, ending any pause, and the halt keeps that row centred. Rows get `.match` or `.focused`. The pill's room is in every max-scroll computation: `centre` and `resize` (`roomPx`), the scroll clamp and the space's height.

### Responsiveness (hard requirement)

The queue, stored playlists, search and anything slow must not make now-playing updates, controls, the mode switch or scrolling any slower. Every queue operation, server and client, runs in the background, on demand, in small pieces.

- **Server:** the queue connection and the non-blocking WS loop (see "MPD bridge" → "Queue").
- **Client:** queue data lives in its own store, fed by `ws.ts` directly, bypassing `App`'s snapshot state. The list element gets only the queue length and the store, memoized on the length (the store is one object for the app's lifetime; Preact skips an identical vnode, no `preact/compat`), so pushes changing anything else don't re-render it. Mode, current song and search matches reach the list through the store (`show(mini)`, each snapshot's `queue`, `search(view)`; see "Wiring"), so no list work runs ahead of now playing.
- **Scrolling:** a passive listener, one pass per animation frame, a re-render only when the rendered range changes; rows positioned with `transform`, no layout reads in loops.
- **Checks** (headless Chromium against the real queue; method in `development.md`): with any change touching the queue, lyrica adds at most ~2–3 ms from MPD's own `idle` event to the DOM change, also while the list loads and scrolls (from the event, not the command: `next` takes MPD 3–237 ms to open a file, more over NFS); `mpc` pause/play stay within 2–4 ms end to end; no long tasks (> 50 ms) during a fling; the mode switch keeps every frame.

Set on each change and each `playing`, in case the browser dropped it. The cover comes from `useCover` in `app.tsx`, shared with the art: no extra requests.
  - **Latency:** no buffering or catch-up of our own: playback starts at `canplay`, and the browser picks its buffer (`<audio>` offers no control). Cutting latency by seeking or reloading would skip audio; latency is the better trade. Stalls (the stream arrives in bursts) grow the buffer, so latency can drift up; toggling off and on resets it.
  - **iOS:** background and lock-screen playback in home-screen apps since iOS 15.4 with `<audio>` (Web Audio is suspended in the background); Ogg Opus needs 18.4. Setting `src` before every `play()` avoids iOS 26 home-screen apps playing silence after a relaunch (WebKit bug 295518). A home-screen app paused in the background for ~30 s can't be resumed from the lock screen until opened.
- **Album art:** a square, always present, the image fitted and centred (`object-fit: contain`). Full mode: centred in the space above the section, edge to edge (`100vw`), capped at 600 px and, on short or landscape screens, at that space minus 20 px above and below. Mini mode: left, as tall as the whole section (`5.125rem + 90px`, 172 px). While the cover for `folder` is unknown (probing, before the first snapshot) the square is empty; then the cover or the placeholder (`src/assets/no-cover.png`). No `folder` (offline, no song, streams, no `--music-url`): the placeholder.
  - **Probing (`cover.ts`):** for a new folder, `cover.{jpg,JPG,png,PNG,jpeg,JPEG}` (the mirror is case-sensitive) load in parallel as `Image`s, so a miss costs one round trip; the first in that order that loads and decodes wins, and decoding first makes it paint at once. Runs after the state renders.
  - **No flicker:** results, hits and misses, are kept per folder URL for the session, so same-folder changes change nothing and revisits show in the same frame as the title. A cover added to the mirror, or a probe failed by the network, is retried only after a reload.
- **Marquee (`marquee.tsx`):** every one-line text that may not fit, in now playing and the queue rows. Too-wide text waits 1 s, scrolls at 50 px/s until its end shows, waits 1 s, scrolls back, repeating. One Web Animations `translateX` animation on an inline-block span, run by the compositor; distance and duration come from a `ResizeObserver` (rotation, the web font loading), the only width read, after layout. Fitting text doesn't animate; a text change restarts it.
  - **Only on screen:** a running animation still costs a style update per frame and a paused one keeps its compositor layer, so an `IntersectionObserver` cancels it off screen (the list's clipped margins included) and restarts it on return. `paused` freezes it in place and restarts it when cleared; the list passes `!store.shown`, so hidden rows cost nothing (see "Measurements" → "Queue marquees").
- **Title, artist, album:** fixed-height marquee lines. The title (a placeholder when `null`); the artist below, smaller and muted (the album artist when there is none, server-side); the album below, 13 px and muted (the folder name when there is none), spanning the full row (the chevron sits beside title and artist only). Empty lines keep their height. The time shares the bar's row, leaving a line for the album.
- **Progress:** the pure `position(snapshot, now)` (`progress.ts`, Vitest) gives the displayed seconds. A `requestAnimationFrame` loop runs only while playing and writes the bar (`transform: scaleX`) and the `m:ss / m:ss` text through refs (text only when it changes), so Preact doesn't re-render per frame. `duration` `null` (streams): empty bar, elapsed only.
  - **Seeking:** in full mode while playing or paused with a known `duration`; otherwise `aria-disabled` and inert. Pointer events with capture on a 44 px box around the bar (into the gaps around its 1rem row; `touch-action: none` only while enabled). Down and every move set the shown position and thicken the bar (4 → 8 px); release sends one `seek`, cancel nothing; switching to mini cancels. Keyboard: `role="slider"`, arrows ±5 s.
  - **Drag tip:** while dragging, a bordered box with the position as a percentage follows the pointer within the bar's ends, exactly over the album line, above the finger.
  - **No jump back:** after a seek the sent position shows, advancing while playing, until the next push or for at most 1 s (MPD rejected it).
  - **Time beside the bar:** a 1rem row, the bar (`flex: 1`) centred vertically, the time right-aligned in a fixed-width box sized by invisible text in the same grid cell (`timeSizer` in `app.tsx`): `00:00 / 00:00` (90 px; tabular digits fit any time under an hour and any stream's elapsed time), `0:00:00 / 0:00:00` from a 1 h duration, `00:00:00 / 00:00:00` from 10 h. Ticking never changes the bar's length. Bar: 248 px in full mode at 390 px; 60 px in mini (45 at 375).
- **Layout:** one column for iPhone portrait; `.app` is a full-height (`--app-height`) flex column, the queue area (`flex: 1`) above the now-playing section, so bar and controls stay put at the bottom. Touch targets ≥ 44 px, safe-area padding (top: `--top`).
- **Fixed viewport:** the document never scrolls or zooms: `html`/`body` have `overflow: hidden`, `overscroll-behavior: none` (no iOS bounce, no Chrome stretch or pull-to-refresh) and `touch-action: pan-x pan-y` (no pinch or double-tap zoom; a descendant's effective `touch-action` intersects its ancestors', so this covers the page). iOS Safari ignores `user-scalable=no` and `maximum-scale` for pinch zoom, so the viewport meta omits them. Scrolling lists are their own scroll containers. Text inputs are ≥ 16 px, or iOS zooms on focus.
- **No selection:** `user-select: none` (and `-webkit-`) on `:root`; text inputs set `user-select: text`.
- **Screen stays on (`wake.ts`):** a Screen Wake Lock while the page is visible, requested again on `visibilitychange` to visible (the system releases it when hidden) and, if refused, on the next touch. Needs a secure context; iOS Safari 16.4+, home-screen apps since iOS 18.4 (WebKit bug 254545).
- **Full height (`--app-height`):** `100dvh`, except in iOS home-screen apps, where `100dvh`, `100svh`, `innerHeight` and percentages come out short by `safe-area-inset-top` (WebKit bug 254868); there `100vh`, the full screen. An inline script in `index.html` adds `.standalone` to `<html>` when `navigator.standalone`, before first paint (`display-mode: standalone` is unreliable on iOS). `html`/`body` have no `height: 100%` or `position: fixed`: a fixed root takes the short viewport and clips `.app`'s bottom.
- **Modes:** the section is a grid with the same rows (title, artist, album, progress, controls) and height in both modes. Full mode positions the art absolutely against `.app`, between `--top` and the section (fixed at `5.125rem + 138px`, so CSS can compute the band); mini puts it in a left column spanning every row, the rows right of it (the bar keeps its right end). The queue area keeps one geometry, only fading in (mini) or out (full, then `visibility: hidden`).
  - **Chevron (`.switch`):** top right, beside title and artist in both modes, so it never moves; pointing down in full mode, up (rotated) in mini. Not persisted: the app always opens in full mode.
  - **Animation (FLIP, `useFlip` in `app.tsx`):** on a click every `[data-flip]` element's drawn rect is recorded, the layout switches in one render, and each element animates from old to new rect with `transform` only (Web Animations, 350 ms, `cubic-bezier(0.4, 0, 0.2, 1)`). Art and bar also scale (`data-flip="scale"`, the art uniformly); text and transport only translate, so nothing stretches. The queue fade and chevron rotation are CSS transitions with the same timing. Rects are recorded before cancelling running animations, so a click mid-switch reverses from where things are drawn. `prefers-reduced-motion: reduce`: instant.
  - **Mode toggles** stay put and fade: out in 80 ms, before the transport reaches them; in after 250 ms, once it has left (tightest at 375 px).
  - **No overflow:** going full, the full-width rows start at their mini offset, past the right edge; `.app`'s `overflow: clip` keeps desktop browsers from flashing a horizontal scrollbar.
- **Font:** Iosevka Aile, Regular (400) and SemiBold (600, title): woff2 from the upstream `PkgWebFont-IosevkaAile` release (nixpkgs has only TTF/TTC), fetched by the flake and bundled by Vite under hashed `assets/` names, cached immutably (~1.6 MB per weight, unsubset). `font-display: swap`; fixed line heights keep the swap from moving anything.

### Live queue

The current MPD queue, read-only. `queue.tsx` is the list, `virtual.ts` its arithmetic, `queue-store.ts` the entries (both Vitest), `cover.ts` the cover probes shared with now playing.

- **Shown only:** entries load and covers are probed only while the list is shown (mini mode, page visible). `App` calls `store.show(mini)` in a layout effect; opening centres and plans at once, so the current song's block loads during the 350 ms fade-in. No background preloading: the visible rows fill within the fade-in's first frames (see "Measurements" → "Opening").
- **Virtual list:** only the rows in view plus 15 on each side exist, a pool of `ceil(clientHeight / 56) + 31` rows recycled by slot (position modulo pool size, the Preact key), so scrolling rewrites rows instead of creating them. Rows are 56 px (`ROW_PX`, ≥ the 44 px touch target, the same for every row), placed with `transform: translateY` in a sizer div (`.queue-space`), so position ↔ offset is arithmetic. Unloaded rows are empty rows of the same height, filled in place.
  - **Bounded space:** browsers cap element heights (~33.5 M px in Chrome and WebKit, ~17.9 M in Firefox: ~300k rows), so the scrolled content is `min(length, 18000)` rows (`SPACE_ROWS`, ≤ 1,008,000 px) mapped onto the queue through an anchor, the queue position of its first row: queue offset = anchor × 56 + `scrollTop`, 0 ≤ anchor ≤ length − space rows. The queue length is unbounded.
  - **Re-anchoring:** once scrolling stops (no `scroll` for 150 ms, `SETTLE_MS`, and no touch held) with the viewport's top outside the space's middle half, the anchor moves (clamped) to put the viewport mid-space and `scrollTop` moves by the same whole rows, in the layout effect of the render applying it: nothing moves on screen. It waits because setting `scrollTop` cancels iOS momentum scrolling. Rare: a quarter of the space (4,500 rows) then lies ahead either way, more than a fling covers.
  - **Edges:** the clamped anchor makes the space's edges the queue's, bounce included; `scrollTop` reads are clamped to the space (WebKit reports positions beyond it during the bounce). A length change clamps the anchor and keeps the queue position at the viewport's top where it still exists; length 0 renders no rows.
  - **Scroll handling:** the passive scroll listener only schedules one animation-frame pass, which reads `scrollTop` and re-renders when the first rendered row changes. `clientHeight` comes from a `ResizeObserver`. `overflow-anchor: none`, so Chrome's scroll anchoring never fights a re-anchor.
  - **Semantics:** `role="list"`, rows `role="listitem"` with `aria-setsize` (length) and `aria-posinset` (position + 1).
  - **No scrollbar** (`scrollbar-width: none`; Chrome 121, Firefox 64, Safari 18.2): it would span the space, not the queue, so dragging it would land anywhere and re-anchor under the pointer. Other scrolling is unchanged; classic-scrollbar desktops get their gutter back.
  - **Scroll container:** `.queue-list` (`overflow-y: auto`, `overscroll-behavior: contain`), as the document never scrolls; vertical panning comes from the root's `touch-action: pan-x pan-y` (nothing narrower on the list). Hidden in full mode by `visibility: hidden`, never `display: none`, so it keeps its size and `scrollTop` and is placed before the fade-in.
- **Blocks (`queue-store.ts`, `QueueStore`):** entries are cached in blocks of 100 positions (`BLOCK`), tagged with the queue version they were read at. Each request is one block: `{"type":"queue","version","start":100b,"end":min(100b + 100, length)}`.
  - **Wanted:** blocks overlapping the visible rows plus two viewports above and below (`AHEAD_VIEWPORTS`, also the covers' range), visible first, then nearest, ties below first.
  - **At most two in flight**, each until its reply. Planning runs on each view report (every scroll pass), reply and show, sending the nearest wanted block neither held nor in flight; so a fling queues nothing stale.
  - **Replies:** stored when for the current version and within the kept range. `[]` (the queue shrank; its push follows) marks the block empty for this version, not retried. `null` frees the slot and retries after 1 s. An older version is dropped.
  - **Kept range:** the visible rows ± 1,000 (10 blocks a side); farther blocks are dropped on each view report, so ~22 blocks (~2,200 entries) at most.
  - **Version, offline, reconnects:** a new version keeps only the blocks overlapping the visible rows (see "Auto-update"); `queue: null` drops everything. Every socket open frees the in-flight slots (an old socket's replies never come; the visibility reconnect closes it without an offline snapshot) and keeps the blocks for the fresh snapshot's version to judge.
  - **Wiring:** `connect(onSnapshot, onConfig, store, onSearch)`. The store implements `opened(send)` (each socket open: the window sender; slots freed), `state(queue)` (each snapshot's `queue`, before `onSnapshot`; `null` on close) and `reply(version, start, songs)`. It exposes `current` (`{ position, id }`, both `null` offline or without a current song), `shown` (the last `show`) and `searching` (the last `search`). The list subscribes with `subscribe({ stored(start, end), current(), opening(), hiding(), top(), recentre(), searched(left), reveal(position) })`: `stored` per stored block; `current` when `state` changes the position or id; `opening` from `show(true)` before planning; `hiding` from `show(false)` (a re-render pausing the rows' marquees); `top` from `store.top()` (playlist load); `recentre` from `store.recentre()` (cover or album tap); `searched` and `reveal` from search mode. `stored`, `current` and `searched` (unless leaving) only mark the list and schedule its animation-frame pass, so no list work runs inside the WS message handler.
- **Auto-centre (`centre(position, viewportPx, length, roomPx)` in `virtual.ts`):** the current row's centre goes to the viewport's centre: offset `position × 56 + 28 − viewportPx / 2`, clamped to `0 … length × 56 + roomPx − viewportPx` (near the ends the first or last row sits flush); anchor `clampAnchor(position − floor(spaceRows / 2))`; written in the layout effect like a re-anchor. No current song: nothing moves.
  - **Opening:** every switch to mini centres and ends any pause. `opening` makes the list place itself, report the new view (so the first request is the current song's block) and re-render; `show` runs in `App`'s layout effect and Preact re-renders in a microtask, so `scrollTop` is written before the fade-in's first frame.
  - **Song change:** the pass after `current` re-centres if shown and not paused, else only re-renders the highlight: now playing updates in the push's render, the list within a frame. Instant (in random mode the next song can be anywhere). The same id at a new position (queue reordered) re-centres too. Hidden: opening does it.
  - **Pause:** `touchstart`, `wheel`, a mouse `pointerdown` (middle-click autoscroll) and `keydown` on the list pause auto-centring; `scroll` alone never does, as programmatic scrolls fire it too. Each pausing input, and while paused each `scroll`, `touchend` and `touchcancel`, restarts a 15 s timer (`RESUME_MS`), after which it resumes and re-centres once no touch is held. Touch, wheel and momentum scrolling always start with a pause, so centring never writes `scrollTop` during one. A row tap ends the pause.
  - **Cover and album taps:** in mini mode, now playing's cover and the album button (after sending) call `store.recentre()`: centre at once, ending any pause. For the album button the push's song change then centres the album's first entry; if MPD rejects the command the list stays centred. Previous and next don't re-centre (a cover tap does). A running fling would carry on from the centred spot: iOS doesn't stop momentum on a `scrollTop` write, so the list gets `overflow-y: hidden` for two frames (one painted); Chromium applies in-flight fling deltas up to two frames late (~27 px each), so until the list settles (`SETTLE_MS`) every pass re-centres unless the user paused it. No tap highlight on the cover; in full mode its tap leaves the list alone.
  - **Search mode** holds auto-centring (the `current` pass and resume timer don't centre); `reveal` centres a match like a cover tap, halt included. `centre`, `resize` and the scroll clamp include `roomPx` (64 px in search mode, else 0).
- **Highlight:** the row whose `id` is `store.current.id` gets `.current`: its texts in bright orange (`#fe8019`, 5.9:1 on `bg0`; the bar's dark orange, 3.8:1, is too low for small text), same size and weight. By id, so it stays right on old rows across a version change. Search matches get `.match` and `.focused`, by position.
- **Auto-update (`queue-store.ts`):** a new queue version (another client editing or shuffling, tag changes, a playlist load) keeps the visible rows' old entries until their replacements arrive: no blank flash.
  - On a new version the blocks overlapping the last reported visible rows stay, with their old version, whatever its age; other blocks, `[]` markers and retry timers go, and if any block went, `stored(0, Infinity)` re-renders the list.
  - Only current-version blocks count as held, so planning refetches the visible old ones first, two in flight. A current reply replaces the old block (`stored`; rows change text in place); `[]` too (rows blank, the shrink's push follows); `null` keeps the old entries and retries after 1 s.
  - Rows past the new length go at once: `entry(position)` is `undefined` from the length on, and the list renders `length` rows.
  - Position-stable: insertions or removals above the view shift the songs under it; the list keeps the queue position at its top (`resize`). Following moved songs would cost a `plchangesposid` round trip per change; while auto-centring, the current song re-centres anyway.
  - Hidden: the same rule with the last reported view; the next opening requests as usual. Replacing the whole queue takes the same path (one `playlist` event with the new length, see "Queue measurements"); a push showing an empty queue in between would empty the list.
- **Rows:** two lines, padded 20 px like now playing: a 40 px left column for the track number (under the album's cover), then from x = 72 px the title (`0.9375rem` / `1.25rem`) over artist and album joined by `·` (`0.8125rem` / `1.125rem`, muted), each a `Marquee` line; the duration right, centred vertically (`0.8125rem`, muted, tabular, empty when `null`). Every row has the same four cells, empty until loaded, so filling changes only text.
  - **Stripes:** odd positions get `.odd`, a `bg0_s` background; by position, so a song keeps its shade across re-anchors, and empty rows are striped too. Contrast on `bg0_s`: `fg1` 9.6:1, `fg4` 4.7:1, bright orange 5.2:1; the `bg2` separator (1.5:1) shows on either shade.
- **Album grouping:** adjacent entries with the same album form a group, its first row getting a separator. The rule exists once, on the server (`same_group` in `bridge.rs`), so separators, covers and the album button agree by construction.
  - **Same group:** `album` equal and not `null`, and `folder` equal, on converted entries. The folder keeps apart adjacent albums of the same name ("Greatest Hits"); `album`'s folder-name fallback groups untagged folders. Streams and files at the top of the music directory (`album` `null`) are a group each. Without `--music-url` grouping is by album alone.
  - **Group start:** position 0, or an entry not in the group of the one before: each entry's `start` flag, computed per window (see "Windows"). `store.starts(position)` is the flag, `undefined` while unserved. Each block carries its own flags: no wait on the previous block, no versions mixed.
  - **Separator:** group starts other than position 0 get `.group`: a 1 px `bg2` line on the row's top edge, inset 20 px, drawn by `::before`; it appears with the row's text.
  - **Track number:** on every row, centred over both lines (muted, `0.8125rem`, tabular; empty when `null` or unloaded). Four digits fit (in a sample of the real queue ~3 % of entries need four, ~10 % three).
- **Covers:** each group's cover sits over the track column: on the group's first row while it's in view, then pinned 8 px below the list's top while the group scrolls under it, until its last row pushes it off. Every row keeps its track number; the cover hides the one under it, and a non-square cover's letterbox bands show what's beneath. No cover: track numbers only, no placeholder.
  - **Pinning:** each group with a found cover gets a `.queue-album` box over the track column (x 20–60 px) spanning its rendered rows, holding the cover at `position: sticky; top: 8px` (40 × 40 px, `object-fit: contain`). The box's 8 px vertical padding is the cover's inset in a 56 px row, so it rests exactly on its first and last rows. The browser keeps it in place while scrolling; positions set from `scroll` events would trail by a frame on iOS, whose momentum scrolling runs off the page's thread.
  - **Spans (`albumSpans` in `virtual.ts`):** the groups among the pool's rows, from `store.starts`, each from a group start (or the pool's first row, or after unserved rows) to the next group start or unserved row. Thanks to the pool's 15-row margins a box ends on screen only where its group does. Placed with `top` and `height` from `(start − anchor) × 56`, like rows, so re-anchors move them in the same render; recomputed per render, never per frame.
  - **Elements:** one `<img alt="" decoding="async">` per box, after the rows in an `aria-hidden` wrapper with `pointer-events: none`. Keyed by folder and album (plus a count for repeats), so a box keeps its element while its span changes. Boxes are created and removed off screen, except on jumps and when a cover arrives for a group in view. Rows without a `folder` have no cover.
  - **States:** a box only once the folder's cover is found; a miss or unknown result adds nothing. Known results render with the rows' text, so scrolling back shows covers at once.
  - **Probing:** through `cover.ts`, sharing per-folder results and in-flight promises (`findCover`) with now playing, so no folder is probed twice. Nothing is probed for the list in full mode.
  - **Ahead of the view:** a probe downloads and decodes the image, so the list probes around the view while scrolling:
    - **Range:** unknown folders among the visible rows plus two list heights above and below (`AHEAD_VIEWPORTS`; ±21 rows at 580 px), covering every group touching it. The store's wanted blocks span the same range, so group starts and folders are loaded ahead too. Rows beyond the pool's margin have no box yet: the probe fills the HTTP cache for when they enter.
    - **When:** each animation-frame pass (scrolling, blocks or probes arriving, a song change), resize and opening. Centring is a jump: it clears the speed samples, so its pass probes.
    - **Too fast:** no new probes above 100 rows/s (`AHEAD_ROWS_PER_S`; 5,600 px/s), measured on the queue offset over the last 100 ms of passes (`SPEED_MS`; after a pause the previous pass counts as 100 ms ago, so a jump is judged by its size). Below it a row probed two lists ahead is ≥ 200 ms away, longer than most covers take (38–216 ms); above it rows cross the list in under 100 ms. Probing resumes in the first slower pass, or after 50 ms without one (`STOPPED_MS`). A hard fling decays below the limit within a few hundred ms, so covers load during its tail.
    - **Order and cap:** at most 12 list probes in flight (`AHEAD_PROBES`, a 580 px viewport of groups), counted per folder until `findCover` resolves: the visible folders top to bottom, then the scroll's side nearest first, then the other (below first before any movement). Each finished probe schedules a pass, so free slots go to what's nearest then. Started probes run to completion; results last the session.
    - **Cost:** each folder once per session, only around the shown list: per stop in a fresh region 2–14 probes (0.2–10 MB) in typical parts of the real queue, 41–44 misses (~0 MB) where every row is its own folder (see "Measurements" → "Covers ahead of the view"), plus the folders passed below the speed limit.
  - **Arrival:** a finished probe schedules the pass; a found cover also marks the list stale, so any number arriving in one frame cost one render. Results for folders no longer rendered are kept.
  - **Image sizes** (~70 covers sampled across the real queue): median ~150 KB and ~600 px on the long side, 90th percentile ~2 MB / ~1,500 px, largest ~5 MB / ~3,000 px, rare outliers over 10 MB. Used as they are, shared with now playing and the browser cache: thumbnails would need a server hop, and the iPhone shows no cost.
- **Tap to play:** tapping a loaded row sends `{"type":"playid","id"}` with its entry id (`Command::PlayId` → `Client::play_id`, command connection, dropped offline). By id, so an old row plays the song it shows, or nothing if it left the queue (MPD's `ACK`, logged). The push moves now playing and the highlight.
  - One delegated `click` listener: the row from `closest(".queue-row")`, its position from `aria-posinset`, the id from `store.entry`. Browsers fire no `click` for a touch that scrolls or stops a fling, so neither plays; no 300 ms delay, as the root's `touch-action` rules out double-tap zoom. Unloaded rows do nothing; mouse clicks play, middle-click (`auxclick`) doesn't. `App`'s `send` is created once, keeping the list's memo.
  - The current song's row sends nothing (`playid` would restart it); it only centres (in search mode, nothing).
  - The tap ends the pause its own `touchstart` began, so the push's `current` pass centres the tapped row, 3–240 ms after the tap (MPD opening the file). A rejected id moves nothing.
  - Feedback is the highlight only: no `:active` style (a touch can't be told from a scroll at `touchstart`); `-webkit-tap-highlight-color: transparent`, or iOS flashes the whole list grey.
- **Offline:** the list is empty and the store drops every block; refetched after reconnecting.

### Measurements

Headless Chromium (390×844, touch emulation for the queue) against the local MPD unless noted; the queue ones against its real queue (~180k entries, random on), with `--music-url` for covers.

**Now playing:** action to DOM change: `mpc` pause/play/seek/next/prev 2–4 ms, buttons 2 ms, mode toggles 1–4 ms. The bar advances every frame (62 samples/s). A server restart recovers within the 1 s retry; a frozen page's visibility reconnect resyncs the bar within 3 ms. Positions hold across song changes, with or without art. The mode switch settles in 350–380 ms, reverses mid-way from the drawn position, and takes one frame under reduced motion.

**Queue marquees** (main-thread time from `Performance.getMetrics`, a dense spot with 20–21 lines animating on screen): mini, idle 8 s: 0.40–0.45 s task / 0.044–0.051 s style; six touch flings: 0.65–0.69 s, no long tasks; full mode, idle 8 s: 0.12–0.14 s. Desktop CPU, so a phone's share is larger.

**Album art** (HTTP mirror, cold cache): a `cover.jpg` (~100 KB) 38 ms after the title, a `cover.png` (~1.5 MB, after the jpg/JPG misses) 216 ms; misses 404 in ~4 ms. A new folder's square stays empty 9–113 ms, then shows the cover or the placeholder; revisits change in the same mutation as the title.

**Play here** (Opus stream, ~13 KB/s): tap to `playing` 2.2–2.5 s, Chrome waiting for ~32 KB (its format probe); buffered ahead 0.8–2.2 s at the start, 3.1–5.1 s after a minute. Lock-screen artwork follows the title by 13–99 ms (its probe).

**Volume** (scripted fake MPD): a tap sends `setvol` 2 ms later; a 1 s drag sends one per 100 ms, the last the final value, with no jump back.

**Toolbar** (mini): with `--stream-url` 8 buttons, icons 46.6 px apart at 390 px (44.4 at 375); without, 7, 54.3 px apart. The first icon starts at x 20, the last ends 20 px from the right.

**Virtual list:** pool 42 rows at 390×844 (580 px list), 39 at 375×667 (403 px). Six touch flings: the rendered rows covered the viewport in every frame, no long tasks, longest frame gap 16.8 ms. Re-anchors keep the top row and offset; the last row sits flush at the end.
