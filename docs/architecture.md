# Architecture

```
iPhone (PWA) ──HTTPS/WSS── Caddy ──HTTP/WS── lyrica (crates/lyrica) ──TCP── MPD
                                               │  embeds web/ build
                                               └─ uses lyrica-mpd (crates/mpd)
```

How lyrica works today. Planned parts are marked as such; open and upcoming work is in `roadmap.md`. Measurements backing the design are under "Measurements" at the end.

## `lyrica-mpd` (crates/mpd)

Async MPD client library, independent of the web server.

- tokio TCP connections; responses parsed with nom 8 (`Parser` trait API).
- Implements only the commands lyrica needs, added incrementally. Currently: `password`, `ping`, `status`, `currentsong`, `playlistinfo START:END`, `play`, `playid`, `pause`, `previous`, `next`, `random`, `repeat`, `single`, `setvol`, `seekcur`, `listplaylists`, `clear`, `load`, `idle`, and command lists.
- **`Client`** is one connection running one command at a time; responses are framed by line and each line parsed with nom (`OK`, `ACK …`, `key: value`). Typed results (`Status`, `Song`) keep only the fields lyrica uses or is about to use and ignore unknown keys. Multi-song responses (`playlistinfo`) start a new `Song` at each `file` line. `Track` is kept as a number, `None` when it isn't one, so an odd tag never fails a window (MPD reported plain numbers for all 5,000 sampled entries, 2,231 of them with the tag twice).
  - **Queue ranges** (`queue_range`): MPD clamps the end to the queue length and returns nothing for an empty range; a start past the queue's end, or after the range's end, is an `ACK`.
  - **Reads:** `TCP_QUICKACK` is re-armed before every socket read (Linux; `socket2`), see "Socket options" below. Lines are read into their own buffer, then appended to the response: tokio's `read_line` re-validates the UTF-8 of its whole buffer on each call, which made a 100-entry window take 3.1 ms instead of 0.43 and a 200-entry one 10 ms.
  - `ACK` errors leave the connection usable. I/O and protocol errors, or a command future dropped mid-response, leave it out of sync: later commands fail with `Error::Broken` and the caller reconnects.
  - `idle` blocks its connection, so idling needs its own `Client`. Arguments are always quoted; newlines are rejected.
  - The library doesn't reconnect: a connection MPD closed (`connection_timeout`, default 60 s unused) fails its next command, and the server reconnects (see "MPD bridge"). Not implemented: binary responses.
  - **Command lists:** private, used by `replace_queue` (`clear` + `load`) and `play_in_order` (`random 0` + `single 0`, then `playid` when given an id): sent in one write, answered with one `OK` or the failing command's `ACK`, whose index says which. Not transactions: the commands before the failing one stay done. On the real MPD, a gone id got `ACK [50@2] {playid} No such song` with both modes left off; `playid` of the paused current song played it from 0:00.
  - **Stored playlists:** `playlists` (`listplaylists`, names in MPD's order) and `replace_queue`. Nothing that edits them.
- **Connection multiplexing:** slow work must never delay interactive work. The server uses one connection idling for state changes, one for commands and one for queue windows (see "MPD bridge"), which stored playlist listings share, so neither state updates nor commands ever queue behind slow reads.
- Large results (queue, playlists) are always requested in ranges/windows, never wholesale. MPD serves all its clients from one event loop, so a large response delays the other connections too; queue windows stay around 100 entries, under 1 ms of MPD time (see "Queue measurements").

## Server (crates/lyrica)

Thin bridge between the frontend and `lyrica-mpd`.

- axum on tokio; serves the embedded frontend (rust-embed) and the frontend WebSocket at `ws` (relative to the page).
- Configuration via CLI arguments (clap), plus `LYRICA_MPD_PASSWORD` for the password; no disk state.
- Plain HTTP; intended to sit behind Caddy. All frontend URLs are relative so a path prefix works, provided the page URL ends in `/`.
- Setup-specific extensions live here or in `lyrica-mpd` as appropriate, e.g. album art from the HTTP mirror of the music library. The browser loads art directly from the mirror (no server hop, browser caching, no server bandwidth); the server only supplies the folder URL. Art is only ever looked for in the song's own folder (user decision). Same for MPD's `httpd` audio stream: the browser plays it directly from `--stream-url`.

### MPD bridge (`bridge.rs`, `ws.rs`)

- **CLI:** `--listen` (default `127.0.0.1:8080`), `--log` (`EnvFilter` syntax, default `info`). `--mpd <host:port>` (default `127.0.0.1:6600`), optional `--mpd-password` (or `LYRICA_MPD_PASSWORD`, which keeps it out of the process list), sent with `password` after every connect. Optional `--music-url <URL>`: base URL of the HTTP mirror of MPD's music directory (e.g. `https://webmusic.wwared.com/`; a missing trailing `/` is added); without it `folder` is always `null` and no art is shown. Optional `--stream-url <URL>`: MPD's `httpd` output (must be HTTPS when the page is, or it is blocked as mixed content); without it there is no play-here toggle.
- **Idle connection:** a task owns one `Client`. It fetches `status` + `currentsong`, publishes the snapshot, then loops `idle(player, options, mixer, playlist)` → refetch → publish. Snapshot fetches run on this connection, so they never queue behind commands.
- **Command connection:** a task owns a second `Client` and serves an `mpsc` of commands and stored playlist loads from all WS clients, serialized. MPD closes connections unused for `connection_timeout` (default 60 s), so on `Io`/`Broken` it reconnects and retries the command once; the closed connection never executed it. `Ack` is logged, not retried.
- **Snapshot fan-out:** `tokio::sync::watch`. Each WS client gets the current snapshot on connect, then every change. While playing, `elapsed` is advanced to the send time, so late subscribers get the current position.
- **MPD unreachable:** the idle task publishes an `offline` snapshot and reconnects with backoff (1 s doubling to 10 s). Commands sent while offline are dropped with a log line; loads get an error reply.
- **WS protocol:** JSON text messages (serde). Revisit only if size or speed proves a problem.
  - Server → client, first on every connection: `{"type":"config","stream":string|null}`, `stream` being `--stream-url` verbatim.
  - Server → client: `{"type":"state","state":"play"|"pause"|"stop"|"offline","title":string|null,"artist":string|null,"album":string|null,"folder":string|null,"elapsed":number|null,"duration":number|null,"volume":number|null,"random":bool,"repeat":bool,"single":bool,"queue":{"version":number,"length":number,"position":number|null,"id":number|null}|null}`. `title` is the `Title` tag, falling back to the file name; `null` when there is no current song. `artist` is the first `Artist` tag, falling back to the first `AlbumArtist`; `album` the first `Album` tag, falling back to the name of the file's folder (none for streams or files at the top of the music directory); `null` when missing. `folder` is `--music-url` plus the song's directory with each path segment percent-encoded (RFC 3986 unreserved characters kept), ending in `/`; `null` without `--music-url`, without a song, or for streams (`file` containing `://`). `folder` and the `AlbumArtist` and folder-name fallbacks come from the `currentsong` response already fetched, so they cost no extra MPD round trip. `elapsed`/`duration` are seconds (fractional) from `status`. `volume` is MPD's volume (0–100) from `status`, `null` when MPD reports none (no mixer, or none open: the local MPD, its output disabled, has none); the bridge also idles on `mixer`, so other clients' volume changes are pushed. `random`/`repeat`/`single` are the modes from `status` (`false` while offline); `single` is also `true` for MPD's `oneshot`. Consume is deliberately absent (unused). `queue` is the queue's version, length and the current song's position and id, from `status` (`playlist`, `playlistlength`, `song`, `songid`); `position` and `id` are `null` when there is no current song, `queue` is `null` while offline. The bridge also idles on the queue subsystem (MPD's `playlist`), so a queue change pushes a new state. Queue entries never travel in the state message.
  - Client → server: `{"type":"previous"}`, `{"type":"toggle"}`, `{"type":"next"}`, `{"type":"random"}`, `{"type":"repeat"}`, `{"type":"single"}`, `{"type":"volume","volume":0–100}` (`setvol`, MPD's global volume, like `mpc volume`; MPD rejects more than 100 and the rejection is logged), `{"type":"seek","position":seconds}` (`seekcur`, absolute, millisecond precision; negative or out-of-range positions are invalid; MPD rejects it while stopped), `{"type":"playid","id":n}` (`playid`, a queue entry's `id` from a window; MPD rejects an id no longer in the queue, logged), `{"type":"albumstart"}` (see "Queue actions"), queue window requests (see "Queue") and stored playlist listings and loads (see "Stored playlists"). Invalid messages are logged and ignored.
  - No replies to commands: the state push triggered by `idle` is the confirmation. Measured on the local MPD (WS client to state message): `toggle` 0.4–1.8 ms, `next` 19 ms, `previous` 3 ms; via `mpc` (including process spawn): `pause` 1.5 ms, `play` 40 ms, `seek` 8 ms. After killing the proxy, `offline` arrives in 40 ms; the first command after a lost connection or a 65 s idle gap reconnects and succeeds in < 2 ms. MPD does not time out connections in `idle`.
- **Toggles** are mapped by the server from the latest snapshot. `toggle`: `play` → `pause(true)`, `pause` → `pause(false)`, `stop` → `play()`. `random`/`repeat`: set to the opposite of the current mode. `single`: on (including `oneshot`) → `single 0`, off → `single 1`. Never send a command that changes nothing: MPD emits no idle event for it, so the frontend would get no update.
- **Queue:**
  - **Queue connection:** a third `Client`, owned by a task serving window requests and stored playlist listings from all WS clients over a bounded `mpsc` (capacity 64), one at a time. Connected on the first request, with the command connection's reconnect-and-retry-once rule (one shared helper). Never the idle or command connection, so state pushes and commands never wait on queue reads.
  - **Socket options:** every MPD `Client` sets `TCP_QUICKACK` before each read (Linux resets it), avoiding the 40 ms stalls (see "Queue measurements"); done in `lyrica-mpd`. Over the VPN a segment holds ~1.4 KB instead of loopback's 64 KB, so even a tag-heavy `currentsong` on the idle connection can span segments; the cost is one `setsockopt` per read. Accepted HTTP / WS connections get `TCP_NODELAY` (axum doesn't set it; `axum::serve::ListenerExt::tap_io` on the listener): with Nagle, a state push sent right after a window reply would wait for the proxy's delayed ACK, the same 40 ms on the path that must stay instant. `TCP_QUICKACK` doesn't help there: it only changes our ACKs for what we receive, a few tiny commands.
  - **Windows:** client → `{"type":"queue","version":n,"start":n,"end":n}` (positions, `end` exclusive; `start` > `end` is invalid, logged and ignored like other invalid messages). Server → `{"type":"queue","version":n,"start":n,"songs":[…]|null}`, `version` and `start` echoed, `version` unread. Every valid request gets exactly one reply.
    - **Cap:** at most 200 entries (0.8 ms of MPD time, see "Queue measurements"); `end` is clamped to `start + 200`, so nothing can request the whole queue. `songs` may be shorter than asked: clamped, or past the queue's end (MPD clamps). `start` = `end` replies `[]` without asking MPD.
    - **Read with the entry before:** for `start` > 0 the server reads `start − 1 … end` in one `playlistinfo` (one queue version, so the flag never mixes versions), uses the leading entry only for the first entry's `start` flag, and drops it. The cap counts the requested entries. So `start` = length reads one entry and replies `[]`.
    - **`[]` vs `null`:** MPD rejecting the range (`ACK`, e.g. `start` past the end after the queue shrank) replies `[]`: nothing there, and a state push with the new version follows. `null` means not served, retry later: the queue task's channel was full, MPD is offline, or MPD was unreachable after the retry. Requests from a connection that has closed meanwhile are skipped.
    - **Entries:** `{"id":n,"title":s,"artist":s|null,"album":s|null,"track":n|null,"duration":n|null,"folder":s|null,"start":bool}`, only what the list shows, positions implied by `start`. Same fallbacks as the state message (title → file name, artist → album artist, album → folder name), from the same helpers. `start`: whether it starts an album group (see "Album grouping"). MPD sends every tag (300–1100 B per entry here); the server forwards a fraction of that.
  - **Consistency without locking:** the client tags each request with the version it has and drops replies for an older one. A window read just after a queue change, before its state push arrives, is stored under the old version and dropped when the push lands: at worst a refetch, never stale rows shown as current.
  - **The WS loop never waits on the queue:** requests go to the queue task with `try_send` (full: an immediate `null` reply); each request carries the connection's reply sender, an unbounded per-connection channel (bounded in practice by the request channel's capacity), so the queue task never waits on a slow WS client either. The loop's `select!` is `biased`: state changes first, then window replies, then incoming messages, so a pending reply never delays a state push. Replies are small (≤ 200 entries, a few tens of KB). Window requests are a separate client message type from `Command`, routed in `ws.rs`.
- **Stored playlists** (frontend: "Stored playlists" under "Frontend"):
  - **Listing:** client → `{"type":"playlists"}`; server → `{"type":"playlists","names":[…]|null}`, to that client alone. Served like a window: the queue task's channel (`try_send`), skipped for a closed connection; `listplaylists`, names sorted case-insensitively by code point (ties: upper case first). `null`: the channel was full, MPD is offline (not asked), or MPD failed (`ACK`, or unreachable after the retry).
  - **Loading:** client → `{"type":"load","name":s}`; server → `{"type":"loaded","name":s,"error":s|null}`, to that client alone, once MPD answers. On the command connection, in order with commands (one channel of `Job::Command` / `Job::Load`): `listplaylists`, then `replace_queue` only if the name is listed, both inside one call of the retry helper (a retried `clear` + `load` is harmless). Errors: `"MPD offline"` (not asked), `"Busy"` (command channel full: refused at once via `try_reserve`, so the WS loop never waits to queue a load), `"No such playlist"` (not listed, queue untouched), MPD's `ACK` message (e.g. `"Playlist is too large"`), or the connection error's text.
  - **During a load** MPD serves no one: state fetches, windows, listings and commands from every client wait. Commands queue in their channel (16); once it's full, a WS loop sending one more waits too, holding back that client's state pushes, which MPD isn't producing anyway. The loading client's modal box stops its own taps.
  - **Over the WS** (release build, two Bun clients, throwaway MPD): listing 0.6 ms (7 playlists). `loaded` after 1.1 / 10.8 / 107 ms for 1,000 / 19,000 / 195,000 songs, 2.53 s for 195,000 over 4,000 directories; a listing sent just after that load came back with its `loaded`. The other client got exactly one state push per load, already with the new length. A missing name: `"No such playlist"` in 0.3 ms, no push; over the limit: `"Playlist is too large"`, queue at 200,000; one missing file: loaded, 3 songs; a name with quotes and non-ASCII: loaded.
- **Queue actions** (frontend: "Queue actions" under "Frontend"):
  - **Album start:** client → `{"type":"albumstart"}`: random and single off, then the current song's album group plays in order from its first entry; repeat untouched. A command like the others: command connection, in order (a `next` sent just before is seen), dropped while offline, no reply (the state push confirms). Inside one call of the retry helper, which reruns it whole, fresh `status` included. `status`; no current song: nothing. Otherwise the walk finds the group's first entry, then `play_in_order` (one command list): `random 0`, `single 0` and `playid` with that entry's id, which plays it from 0:00, also when it is the current song paused or stopped. Only when the first entry is the current song and playing is `playid` left out, so it carries on. The modes go even when already off, unlike the toggles' rule: the frontend re-centres itself rather than waiting for a push, so a no-op costs nothing.
  - **The walk** (`group_start`): `playlistinfo` backwards in windows of 100, the first ending at the current song; entries converted like a window's (`Entry::new`, which is why the command task gets `--music-url` too: `folder` takes part in the rule) and compared with `same_group`, across window edges too. Stops at the first entry outside the group or at position 0. Usually one window; no cap: a group spanning the whole 175,872-entry queue would take ~1,760 windows, ~0.8 s at 0.43 ms each (estimate, see "Queue measurements"), with other connections served between them.
  - **Races:** a queue change between `status` and the reads may `ACK` (logged) or pick another group; `playid` is by id, so it never plays an entry that left the queue.
  - **Over the WS** (debug build, Bun client, real MPD, `--music-url`): from the third entry of a 65-entry group with random and single on: the group's first entry at 0:00, random and single off, repeat still on, queue version unchanged. Sent again with that entry playing: no state push, playback carried on (4.1 s in at the next pause). Sent while it was paused: playing from 0:00.
- **Queue measurements** (local MPD 0.24, 175,872-entry queue, raw TCP client): `status` 0.09 ms. `playlistinfo` of 100 entries 0.4–0.7 ms and 31–114 KB, 300 entries 1.2 ms / 180 KB, 1000 entries 4.5 ms / 654 KB; the whole queue 132 MB in 10.7 s. `plchangesposid` for the current version: empty, 0.24 ms.
  - **~40 ms stalls from delayed ACKs:** in runs of 20 windows, 7–18 of the 25-, 50- and 100-entry ones took 40–43 ms, none of the 10- or 200-entry ones, with or without `TCP_NODELAY` on the client. Setting `TCP_QUICKACK` before every read removed all of them (25 / 50 / 100 entries: 0 of 20 stalled, medians 0.09 / 0.15 / 0.24 ms). So MPD holds the last segment of a response until our ACK arrives, which Linux delays by 40 ms; not storage (`playlistinfo` is served from memory). Responses within one segment never stall.
  - **`lyrica-mpd` client** (release build, 40 windows per size spread over the queue, two runs): medians 0.07 / 0.13 / 0.23 / 0.43 / 0.82 ms for 10 / 25 / 50 / 100 / 200 entries, maximum 1.3 ms, no stalls; `status` and `currentsong` 0.02–0.03 ms. With the `TCP_QUICKACK` line disabled: 25 / 39 / 28 of 40 windows of 25 / 50 / 100 entries and 2 of 40 of 200 took 41–42 ms; 10 entries never.
  - **Over the WS** (release build, Bun client): request to reply 0.29 ms for 3 entries, 0.81 ms for 200 (30 KB). Worst case, a separate client fetching random 100-entry windows back to back, two in flight (~2000 windows/s, median 0.9 ms, 0 `null`): what lyrica adds after MPD's `idle` event, to the DOM in headless Chromium, rose from 0.44 to 1.41 ms median for pause / play (max 1.75) and from 0.82 to 1.93 ms for `next` (max 2.30), 12 each; the state push on the loaded connection itself came 0.7–1.6 ms after the event. The same load sent straight to MPD instead (2.5× the rate) raised them to 1.16 / 1.67 ms: most of the increase is MPD answering the idle connection's `status` and `currentsong` between window reads, not the WS loop. Windows stall only while MPD opens the next file (max 155 ms, during `next`).
  - **Loading stored playlists** (`replace_queue`, throwaway MPD 0.24.15, `.m3u` files, release build): 1,000 / 19,000 / 195,000 songs in 1–9 / 10–17 / 83–105 ms, the upper ends when clearing 195,000 entries first. MPD answers no one meanwhile: a second connection's `status` waited out the whole load each time. An `idle playlist` client got one `playlist` event per load (plus `player` when it stopped playback), and `status` right after already showed the new length: no empty queue in between, though the version moves by 2. Per-song cost is MPD's database lookup, which grows with directory width: with 195,000 lines into 4,000 sibling directories, `load` took 2.66 s and `playlistlength` 2.50 s (the ordinary 195,000 file: 105 / 79 ms). On the real MPD, `playlistlength` takes 1.9 / 17.4 / 19.2 s for its 19,288 / 175,905 / 195,193-song playlists, blocking `status` likewise, so loading them should take about as long, with MPD frozen for every client meanwhile (an estimate: the real queue is never replaced in development). `listplaylists`: 0.05 ms median.
  - **Failed loads** (throwaway): a missing name → `ACK [50@1] {load} No such playlist`, queue left empty; a playlist over `max_playlist_length` → `ACK [51@1] {load} Playlist is too large`, queue filled up to the limit; missing files inside a playlist are skipped without an error.
  - **Queue search** (`playlistsearch`, MPD 0.24.0, same queue; MPD serves no one during a scan). Measured while designing search (see "Search (planned)").
    - **`contains` vs regex**, full scans without a match: `contains` on title 125 ms, artist 85, album 143, file 351, `any` 1,640, title + artist + album + file 610–650; the same with regex (`=~`) 59–63 ms, `any` 126. Same positions as `contains` for 8 terms over those four fields, except non-ASCII case (`BJÖRK`: regex 0, `contains` 1) and ß (`contains` folds it to ss).
    - **Byte mode:** `bj.rk` misses "Björk", `bj..rk` finds it, `[öÖ]` never matches. With `(*UTF)` in front: `BJÖRK` finds it, `Σ` 37 titles against `σ`'s 7, `STRASSE` misses "Straße"; +15 ms per scan.
    - **Default fields** with `(*UTF)`, title, artist, albumartist, album, file: 88 ms, 77 with file first; without file 66; title + artist + album 56. `any` 142.
    - **Several terms:** `AND` stops at the first false operand. Two words 82–91 ms; three, the first common, 113; a rare word then a negated one 82; a negated term first 140 (nearly every entry passes it), three negated first 263.
    - **Windows:** `window 0:5` of a common term 1.2 ms (the scan stops once the window is full). `window k:k+1`: 0.1–42 ms up to the k-th match, a full scan (~60 ms) when there is none, 0.1 ms past the queue's length. 500 matches 1–60 ms, 165–680 KB (every tag of every match). Unwindowed, title `a` (110,600 matches): 5.2 s, 84 MB.
    - **Missing:** `OR` (`'AND' expected`) and position filters (`Unknown filter type: pos`); `!((… !~ …) AND …)` works as `OR`. An invalid regex: `ACK … Error in regex at offset 1: missing closing parenthesis`; so is a `(*VERB)` past the start.
    - **Counting** by bisection on `window k:k+1` (1,000, doubling, then halving), a second connection polling `status` every 5 ms: "love" 3,156 matches in 14 probes, 863 ms; "the" 47,646 in 22, 1,051 ms; "a" 174,202 in 26, 645 ms. Longest probe 67 ms; each `status` waited out one probe: median 34–61 ms, max 62.
    - **Decomposed accents** (combining marks U+0300–036F): 5 titles and 5 paths, no artist or album.

## Search (planned)

Finds matches in the live queue with MPD's `playlistsearch` and centres the list on them one at a time, without playing them. Implementation steps are in `roadmap.md`; measurements under "Queue measurements" → "Queue search".

### Behaviour

- **Button:** Material's `search` icon in the toolbar's second slot, after the stored playlists button. The toolbar becomes one evenly spaced row of 44 px buttons (`justify-content: space-between`): with search, 8 in 352 px, icons 46.6 px apart at 390 px, 44.4 at 375; the first icon still starts at x 20, the last ends 20 px from the right. Disabled offline.
- **Search mode:** the button turns the toolbar into `[✕][input][🔍]`, the input focused. Input: `type="search"`, 16 px font (iOS zooms in on smaller), `user-select: text`, `enterkeyhint="search"`, autocorrect, autocapitalize and spellcheck off.
- **Submit:** Return or 🔍 closes the keyboard and runs the query; a blank query does nothing. The query stays in the input, editable, and 🔍 stays. Every submission, the same query included, replaces the matches, as if search mode had been left and entered again.
- **Pill:** while a search is active, `( ▲  3 / 120  ▼ )` over the list's bottom edge. ▲ previous, ▼ next, wrapping at the ends. While the server works, the "Loading…" box's spinner in place of the count; the total reads `…` until counted.
- **Room for the pill:** in search mode only, the list's content ends in empty space as tall as the pill's footprint, so the last row can be centred or rest above the pill.
- **First match:** the first after the current song, wrapping to the queue's first; from the top with no current song.
- **Focused match:** centred instantly, like auto-centring; never played. Matching rows (among the known matches) get a subtle background; the focused one `bg2` and yellow text, like the playlists dialog's selection.
- **Auto-centring** is off for the whole of search mode: song changes move the highlight, not the list. Scrolling by hand is free; ▲▼ continue from the focused match. Tapping a row plays it; search mode stays.
- **Queue changes** make the matches' positions stale: the next ▲▼ reruns the query and continues from the focused match's position in its direction.
- **Errors and no matches:** a toast in the toolbar's toast spot (parse error, MPD's error such as an invalid regex, offline; "No matches"); search mode stays.
- **Leaving:** ✕, Escape (desktop) or switching to full mode clears the query, restores the toolbar, resumes auto-centring and centres the current song, like a cover tap. Nothing persists.

### Query language

Phase 1 accepts plain words only; phase 2 the whole grammar, parsed with nom. Case-insensitive throughout, field names included.

```
query = term (spaces term)*
term  = ["-"] [field ":"] value
value = "^" atom | atom | "/" regex "/"
atom  = word | '"' text '"'
field = title | artist | albumartist | album | file | any
```

- **Terms** are joined by AND. A term matches when one of its fields does: its field, or the default fields `file`, `title`, `artist`, `albumartist`, `album` (never `any`). Different terms may match in different fields.
- **Word:** substring (`love` finds "Glove"). **Quoted:** substring including spaces; `\"` and `\\` inside. **`^`:** starts with. **`/re/`:** MPD's PCRE2 regex, `\/` for `/`, other backslashes passed on.
- **`-`** negates any whole term: none of its fields matches. Only in front: inside a value it is literal (`artist:-live` contains "-live").
- **Plain text** where nothing else applies: an unknown prefix (`re:zero`), a lone `-` or `^`, `^/x/` (starts with "/x/"), a `/` not starting a term (`AC/DC`).
- **Errors:** an unclosed `"` or `/`.

| Query                          | Matches entries where                                                               |
| ------------------------------ | ----------------------------------------------------------------------------------- |
| `radiohead creep`              | a default field contains "radiohead" and one (maybe another) contains "creep"       |
| `"no surprises"`               | a default field contains "no surprises"                                             |
| `-live ^hello /world wide/`    | no default field contains "live", one starts with "hello", one matches `world wide` |
| `artist:radiohead -album:live` | the artist contains "radiohead" and the album doesn't contain "live"                |
| `-^the`                        | no default field starts with "the"                                                  |
| `file:/\.flac$/`               | the path ends in ".flac"                                                            |
| `re:zero`                      | a default field contains "re:zero"                                                  |

### MPD filters

- **Regex only** (`=~`, negated `!~`): 10× faster than `contains`. Words and quoted text become literals (every ASCII non-alphanumeric character backslashed), `^` prefixes `^`.
- **`(*UTF)`** starts every regex, the user's too: MPD compiles regexes in byte mode, where case folding covers ASCII only and `.` is a byte; `(*UTF)` switches PCRE2 to UTF-8 with Unicode case folding (ö/Ö, σ/ς/Σ). Not covered: multi-character folding (ß ≠ ss), accents (bjork ≠ björk, as with `contains`), accents stored as combining marks (a typed "atún" misses those few entries). A user's `(*VERB)` is still valid right after ours.
- **Several fields** (MPD 0.24 has no `OR`): `(!((file !~ 'r') AND (title !~ 'r') AND …))`; negated `((file !~ 'r') AND …)`; one field `(f =~ 'r')` or `(f !~ 'r')`. Default fields file first (77 ms against 88).
- **Order:** `AND` stops at the first false operand, so positive terms go first, longest literal first (likely the most selective), negated ones last.
- **Quoting, two levels:** the value in single quotes inside the filter, the filter in double quotes as the command's argument; each level backslash-escapes `\` and its quote, so a regex backslash is four on the wire.

### Server

- **`lyrica-mpd`:** `playlistsearch FILTER window START:END` in a command list after `status`, so the queue version belongs to the result (MPD serves no one else during a list); only `Pos` kept.
- **Messages** (draft): client → `{"type":"search","id":n,"query":s,"from":p|null}` starts a search, replacing the connection's previous one (`from`: the current song's position). Server → `{"type":"matches","id","version","start":k,"positions":[…]}`, a chunk: matches k to k + 499 in queue order, k a multiple of 500; shorter means the last. Client → `{"type":"matches","id","query","start":k}` fetches another chunk. Server → `{"type":"total","id","total":n}` once counted; `{"type":"searchfailed","id","error":s}` (parse error, MPD's error, offline); `{"type":"searchend"}` from the client drops its search.
- **Scheduling:** the search runs in the queue task (`serve_reads`), one MPD command per step; before each step, pending windows and listings go first, so they wait at most one probe. One search per connection; a new search, `searchend` or a closed socket drops it. A version change between steps ends it as stale.
- **First match:** chunk 0 first; shorter than 500, everything is known. Otherwise probes (`window k:k+1`, the k-th match's position), k picked by interpolation from the known (index, position) pairs, falling back to bisection, find the first match after `from`, then its chunk. None after it: chunk 0's first.
- **Count:** the same probes find the first k without a match, after the first chunk is sent, with a gap between probes.
- **Limits:** target ≤ 65 ms per MPD command, ceiling 100 ms; anything over the ceiling is investigated, simplified or removed, except phase 2 query shapes kept after trying them by hand (slower searches traded for a more powerful language). Known: a one-word default scan 77 ms (over the target), a negated-only query 140–263 ms and `any` 142 ms (over the ceiling).

### Frontend

- **`search.ts`** (Vitest): pure arithmetic: a match index's chunk, next / previous with wrap, the first index after `from`, the count text.
- **`App`** holds the search state (query, id, version, chunks, total, focused index, pending); the toolbar renders either its buttons or the search bar; the pill sits in the queue area.
- **Store / list:** `reveal(position)`, like `top()` and `recentre()`, centres a row; search mode pauses auto-centring until it ends and adds the room for the pill; rows ask whether they are a match or the focused one.
- **Reused:** the toolbar toast, the loading spinner.

### Responsiveness (hard requirement)

The queue, stored playlists and anything slow added later must not make anything slower: now-playing updates, controls, the mode switch and scrolling stay exactly as fast as without them. Every queue operation, server and client, runs in the background, on demand and in small pieces.

- **Server:** the queue connection and the non-blocking WS loop (see "MPD bridge" → "Queue").
- **Client:** queue data lives in its own store, fed by `ws.ts` directly (queue messages bypass `App`'s snapshot state). The list element gets only the queue length and the store, memoized (`App` builds it in a `useMemo` on the length; the store is one object for the app's lifetime; Preact skips an identical vnode, no `preact/compat`), so state pushes that change anything else (elapsed, volume, modes, the current song) don't re-render it in the push's own render. Mode and current song reach the list through the store (`show(mini)`, each snapshot's `queue`), which notifies it (see "Wiring"), so a mode switch or a song change never runs list work ahead of now playing.
- **Scrolling:** a passive listener, work batched to one pass per animation frame, a re-render only when the rendered range changes; rows positioned with `transform`, no layout reads in loops.
- **Checks**, for every change that touches the queue, in headless Chromium against the real queue, compared with the build before it: after MPD's own `idle` event, lyrica adds at most ~2–3 ms until the DOM changes, while the list loads and scrolls (measured from the event, not from the command: `next` takes MPD 3–237 ms to open the next file, more over NFS, which lyrica can't change); `mpc` pause/play stay within 2–4 ms end to end; no long tasks (> 50 ms) during a fling; the mode switch keeps every frame.

### Now playing

Covers album art, title, artist, album, play state, progress bar and seeking on it, previous / play-pause / next, random / single / repeat, MPD's volume, playing the `httpd` stream here, and the full / mini mode switch.

- **`ws.ts`:** owns the socket and the protocol types (`Config`; `Snapshot`: a `state` message stamped with its `performance.now()` receive time; `Command`). Parses `config`, `state`, `queue`, `playlists` and `loaded` messages (ignores anything else; queue state and entries also go to the queue store, see "Blocks"), exposes `send(command)` (dropped unless open), and `playlists()` / `load(name)`, promises settled by their replies (a closed socket answers at once: `null` / "Not connected"; see "Stored playlists" → "Lost connection"; `requests()` keeps the pending ones, Vitest). Reconnects 1 s after a close. On `visibilitychange` to visible, closes and reopens the socket: the server sends a fresh snapshot on connect (with `elapsed` advanced), which resyncs the bar and avoids zombie sockets after iOS suspends the page; `performance.now()` may not advance while the device sleeps.
- **Offline:** a closed socket is displayed exactly like `state: "offline"`. Buttons are disabled while offline, except the play-here and volume toggles (the volume slider is disabled).
- **No optimistic UI:** buttons only send; the UI changes when the state push arrives (< 20 ms on the local MPD).
- **Play/pause button** shows pause while `play`, play otherwise; sends `toggle`.
- **Control strip:** a three-column grid (`minmax(0, 1fr) auto minmax(0, 1fr)`), so previous / play-pause / next stay centred, with the play-here and volume toggles (`.extras`, 44×44 px each, the first icon lined up with the start of the progress bar) left-aligned in the first column and the mode toggles right-aligned in the third, without shifting them. Transport buttons are 52×56 px; the toggles (random, single, repeat; Material Icons shuffle, looks_one, repeat) are 26×44 px so all three fit beside the centred transport down to 375 px wide screens; at 375 px the volume toggle ends 3.5 px before previous. Off: muted colour; on: the colours under "Dark only" (`aria-pressed`, `aria-expanded`). Each mode toggle sends its mode command; the state push updates it. In mini mode the strip is the column right of the art: the transport is centred there with 48 px buttons and no gaps (fits 147 px at 375 px) and the play-here, volume and mode toggles are hidden (user decision: there is no room for them beside a full-height art); the toolbar holds them instead (see "Player toggles").
- **Volume (`volume.tsx`):** the toggle (Material Icons volume_up, always shown; no level on it) opens a vertical pill: up from the control strip in full mode, down from the toolbar in mini mode (200 ms `clip-path` reveal), the same size in both: 44 px wide, as wide as the toggle, 240 px long, rounded, bordered, opaque, over whatever is there (title, art or the list). The toggle stays on top inside the pill's near end, in the "on" colour, so the pill reads as its slider; then the bar (140 px, 100 at the top) and, at the far end, the level (`–` when `volume` is `null`, then without a thumb). Closed again by the toggle or by switching modes. Each place has its own pill (`direction` `up` / `down`), open only while the toggle is on and its mode is shown: an open pill is `visibility: visible`, which would show through the hidden place. Sets MPD's global volume, not the stream's (MPD applies it to the stream itself).
  - **Input:** pointer events with capture on the slider part of the pill (its full width, so tap or drag anywhere sets the value from the y position; `touch-action: none`), not `<input type="range">`, whose iOS version only follows drags that start on the thumb. Keyboard: `role="slider"`, `aria-orientation="vertical"`, arrows ±5, Home / End.
  - **Throttled, then held:** a change shows at once and is sent at most every 100 ms while dragging, the last value always. The local value stays shown for 1 s after the last change, so state pushes for the intermediate values sent meanwhile don't make the thumb jump back; then the bar follows `volume` again (including other clients' changes). Values equal to the shown one aren't sent.
- **Play here (`stream.ts`):** a toggle (Material Icons headphones), shown only when `config.stream` is set; off/on colours as the mode toggles. Plays MPD's `httpd` output (an endless, real-time Ogg Opus stream) through a detached `Audio`, so the page has no native audio controls. Local state, not persisted; always starts off.
  - **Live, never paused:** on sets `src` and calls `play()` in the click handler itself (iOS only allows `play()` within a gesture); off removes `src` and calls `load()`, which aborts the request. So every on is a new connection that joins the stream at the current point, never a resume from a stale buffer. A `pause` the page didn't cause (iOS lock screen or Control Center, headphones unplugged, a call) turns it off for the same reason; Media Session `play` / `pause` / `stop` handlers map the lock-screen buttons to on / off.
  - **Reconnects while on:** `error` or `ended` (MPD stops and closes the output, the network drops) loads the stream again after 1 s, indefinitely. If `play()` is refused (`NotAllowedError`: a retry without a gesture, e.g. in the background on iOS), it turns off.
  - **Lock screen / Control Center:** Media Session metadata mirrors the page: title (the heading, so also "Offline" etc.), artist, album, and the cover as artwork (absolute URL; the placeholder when there is none; left out while the cover is unknown, so the placeholder never flashes in). Set on every change and again on each `playing`, in case the browser dropped metadata set while nothing played. The cover comes from `useCover` in `app.tsx`, shared with the art, so it costs no extra requests.
  - **Latency:** no buffering of our own and no catch-up: playback starts as soon as the browser can (`canplay`), and the browser picks its buffer, which `<audio>` gives no control over. Seeking or reloading to cut latency would skip audio (user decision: some latency over skips). Stalls (the stream arrives in bursts) grow the buffer, so latency can drift up during a session; toggling off and on resets it.
  - **iOS:** background and lock-screen playback works in home-screen apps since iOS 15.4 with `<audio>` (not Web Audio, which iOS suspends in the background); Ogg Opus needs iOS 18.4. Setting `src` before every `play()` also avoids iOS 26 home-screen apps playing silence after a relaunch (WebKit bug 295518). A home-screen app left paused in the background for ~30 s can't be resumed from the lock screen until it is opened again (accepted by the user).
- **Album art:** a square, always present so nothing jumps; the image is scaled to fit and centred (`object-fit: contain`). Full mode: centred both horizontally and vertically in the space above the now-playing section; edge to edge (`100vw`), capped at 600 px (only reached on desktop/tablet), and on short or landscape screens capped by that space minus 20 px above and below. Mini mode: left-anchored, as tall as every row of the section, controls included (`5.125rem + 90px`, 172 px). While the cover for the current `folder` is unknown (probing, or before the first snapshot) the square is empty, showing only the background; then the cover, or the placeholder (`src/assets/no-cover.png`) when there is none. No `folder` (offline, no song, streams, no `--music-url`) shows the placeholder.
  - **Probing (`cover.ts`):** for a new folder, all of `cover.{jpg,JPG,png,PNG,jpeg,JPEG}` (the mirror is case-sensitive) load in parallel as `Image`s, so a miss costs one round trip instead of up to six; the first in that order that loads and decodes wins. Decoding before display makes the cover paint at once. Runs after the state is rendered, so title and controls never wait on it.
  - **No flicker:** results, hits and misses, are kept per folder URL for the session; a track change within the same folder changes nothing, and returning to a folder shows its cover or placeholder in the same frame as the title. So a cover added to the mirror (or a probe that failed on a network error) is only retried after a reload. A result for a folder that is no longer current is still kept but not shown.
- **Marquee (`marquee.tsx`):** the reusable component for every one-line text that may not fit, now playing's lines and the queue rows' alike. Too-wide text waits 1 s, scrolls (50 px/s) until its end is visible, waits 1 s, scrolls back, and repeats (bouncing, not wrapping). One Web Animations API `translateX` animation on an inline-block span, so it runs on the compositor; distance and duration are recomputed by a `ResizeObserver` (rotation, the web font replacing the fallback), the only place the width is read, after layout, so a render never forces one. Text that fits does not animate. A text change restarts from the beginning.
  - **Only on screen:** a running animation still costs the main thread a style update every frame, and a paused one keeps its compositor layer. So an `IntersectionObserver` cancels it when the line leaves the screen (clipped by its scroll container, like the list's 15-row margins) and restarts it from the beginning when it comes back. `paused` freezes it in place (no jump back while the list fades out) and restarts it when cleared; the list passes `!store.shown`, so its hidden rows in full mode cost nothing (see "Measurements" → "Queue marquees").
- **Title:** `title`, or a placeholder when `null`, in a fixed-height marquee line.
- **Artist:** below the title, smaller and muted, same fixed-height marquee line; the album artist when the song has no artist (server-side); empty (height kept) when both are missing.
- **Album:** below the artist, smaller still (13 px, the size of the time) and muted, same fixed-height marquee line; the folder name when the song has no album (server-side); empty (height kept) when `null`. Spans the full row width (the chevron is beside title and artist only). Added without growing the section: the time moved onto the bar's row, freeing its line.
- **Progress:** the pure `position(snapshot, now)` (`progress.ts`, Vitest) computes the displayed seconds. A `requestAnimationFrame` loop runs only while playing and writes the bar (`transform: scaleX`) and the `m:ss / m:ss` text directly through refs, the text only when it changes, so Preact does not re-render per frame. `duration` `null` (streams): empty bar, elapsed text only.
  - **Seeking:** enabled in full mode while playing or paused with a known `duration`; otherwise `aria-disabled` and inert. Pointer events with capture on a 44 px tall box around the bar (spilling into the gaps above and below its 1rem row; `touch-action: none` only while enabled), like the volume slider. Its box has a fixed width, set by an invisible sizer text in the same grid cell (`timeSizer` in `app.tsx`): `00:00 / 00:00` (90 px), which fits every time under an hour (digits are tabular), and also any stream's elapsed time; `0:00:00 / 0:00:00` from a 1 h duration, `00:00:00 / 00:00:00` from 10 h. Touch targets ≥ 44 px tall, safe-area padding (at the top, `--top`; see "PWA" → "iOS status bar"), colours from the CSS variables.

Lists that scroll (the queue) must be their own scroll containers. Future text inputs need `font-size` ≥ 16 px, or iOS zooms in on focus.
- **No selection:** `user-select: none` (plus `-webkit-` for Safari) on `:root`; descendants inherit it, so no text or image can be selected by drag, double-click or select-all (desktop). Future text inputs need `user-select: text`.
- **Screen stays on (`wake.ts`):** a Screen Wake Lock is held while the page is visible, so an idle phone doesn't dim and lock with the app open. The system releases it when the page is hidden; it's requested again on `visibilitychange` to visible, and a refused request is retried on the next touch. Needs a secure context (HTTPS or localhost); iOS Safari 16.4+, home-screen apps only since iOS 18.4 (WebKit bug 254545).
- **Full height (`--app-height`):** `100dvh`, except in iOS home-screen apps, where `100dvh`, `100svh`, `innerHeight` and percentage heights come out short by `safe-area-inset-top` (WebKit bug 254868), leaving an empty band at the bottom; there it is `100vh`, the full screen since there is no toolbar. An inline script in `index.html` adds `.standalone` to `<html>` when `navigator.standalone` is true, before first paint (`@media (display-mode: standalone)` is unreliable on iOS). For the same reason `html`/`body` have no `height: 100%` and no `position: fixed`: a fixed root is sized to the short viewport and clips the bottom of `.app`. Measured on an iPhone screenshot (402×874 pt): with `100dvh`, `.app` ended at ~812 pt, 62 pt (the top inset) short.
- **Modes:** the now-playing section is a grid with the same rows (title, artist, album, progress, controls) and the same height in both modes. Full mode positions the art absolutely against `.app`, in the band between the content top (`--top`) and the section (whose height is fixed: `5.125rem + 138px`, so CSS can compute the band); mini mode puts it in a left column spanning every row, and all rows move right of it (the bar keeps its right end). So the queue area has one geometry in both modes and never reflows on a switch; it is only faded in (mini) or out (full, then `visibility: hidden`).
  - **Chevron (`.switch`):** at the top right of the mini box (beside title/artist) in both modes, so it never moves; the title and artist lines always leave room for it. Points down in full mode, up in mini (rotated). Not persisted: the app always opens in full mode (user decision).
  - **Animation (FLIP, `useFlip` in `app.tsx`):** on a click, every `[data-flip]` element's drawn rect is recorded, the layout switches in one render, and each element animates (Web Animations API, 350 ms, `cubic-bezier(0.4, 0, 0.2, 1)`) from the old rect to the new with `transform` only, so it runs on the compositor. Art and bar also scale (`data-flip="scale"`; the art is square in both modes, so uniformly); title, artist, album, time and the transport buttons only translate, so text and icons never stretch. The queue area's fade and chevron rotation are CSS transitions with the same duration and curve. Rects are recorded before cancelling running animations, so a click mid-switch reverses from the drawn position. `prefers-reduced-motion: reduce`: instant switch.
  - **Mode toggles** stay in place and only fade: out in 80 ms, before the sliding transport reaches them; in after 250 ms, once it has left (375 px is the tight case).
  - **No overflow:** going to full mode, the full-width rows start at their mini offset, past the right edge; `.app` has `overflow: clip` (no scroll container), which stops desktop browsers from flashing a horizontal scrollbar.
- **Font:** Iosevka Aile everywhere, Regular (400) and SemiBold (600, title). The woff2 files come from the upstream `PkgWebFont-IosevkaAile` release (nixpkgs has only TTF/TTC builds; converting those or building Iosevka from source were the alternatives), fetched by the flake and bundled by Vite under hashed `assets/` names, so they are cached immutably after the first load (~1.6 MB per weight, unsubset). `font-display: swap`; the fixed line heights keep the swap from moving anything.

### Live queue

The current MPD queue, read-only. `queue.tsx` is the list, `virtual.ts` its arithmetic (Vitest), `queue-store.ts` the entries (Vitest), `cover.ts` the cover probes shared with now playing.

- **Shown only:** entries load and covers are probed only while the queue is shown (mini mode, page visible). In full mode nothing loads for the list; opening centres and requests at once. No background preloading (user decision): the visible rows fill within the fade-in's first frames (see "Measurements" → "Opening").
- **Virtual list over a bounded scroll space (`queue.tsx`, arithmetic in `virtual.ts`):** only the rows in view plus a margin of 15 rows on each side exist in the DOM, a pool of `ceil(clientHeight / 56) + 31` rows (at most the queue length) recycled by slot (queue position modulo the pool size, the Preact key), so scrolling and refreshes rewrite existing rows instead of creating and destroying them. Rows are 56 px (`ROW_PX`, ≥ the 44 px touch target; may change with the row layout, never per row), absolutely positioned in a sizer div (`.queue-space`) with `transform: translateY`, so position ↔ offset is plain arithmetic. Rows not loaded yet are empty rows of the same height, filled in place: no spinner, nothing moves.
  - The scrolled content is not length × row height: browsers cap element heights (~33.5 M px in Chrome and WebKit, ~17.9 M px in Firefox, ~300k rows at 56 px). It is a scroll space of `min(length, 18000)` rows (`SPACE_ROWS`, ≤ 1,008,000 px) mapped onto the queue through an anchor, the queue position of the space's first row: queue offset = anchor × 56 + `scrollTop`, 0 ≤ anchor ≤ length − space rows. So the queue length is unbounded.
  - **Re-anchoring:** when scrolling stops (no `scroll` event for 150 ms, `SETTLE_MS`, and no touch held, from passive `touchstart` / `touchend` / `touchcancel`) and the viewport's top is outside the middle half of the space, the anchor moves (clamped) so the viewport sits mid-space again, and `scrollTop` moves by the same amount in whole rows, in a layout effect of the render that applies the new anchor, so nothing moves on screen. Rare by design: after one, at least a quarter of the space (4,500 rows, 252k px) lies ahead in either direction, more than one fling covers. It waits for scrolling to stop because setting `scrollTop` cancels momentum scrolling (iOS).
  - Near the queue's ends the clamped anchor makes the space's edges the real start and end, bounce included. WebKit reports `scrollTop` beyond the space during the bounce (negative at the top), positions with no rows, so every read is clamped to the space. A length change (state push) clamps the anchor and keeps the same queue position at the viewport top where it still exists; length 0 (offline, empty queue) renders no rows. Auto-centring is a placement around the current song (see "Auto-centre").
  - The scroll handler (passive) only schedules one `requestAnimationFrame` pass, which reads `scrollTop` and re-renders only when the first rendered row changes. `clientHeight` comes from a `ResizeObserver`, never read while scrolling. `overflow-anchor: none` on the list, so Chrome's scroll anchoring never fights the re-anchor.
  - Semantics: the list is `role="list"`, each row `role="listitem"` with `aria-setsize` (length) and `aria-posinset` (position + 1), as virtual lists need; the checks read positions from them.
  - **No scrollbar** (`scrollbar-width: none`; Chrome 121, Firefox 64, Safari 18.2, so every iOS version lyrica supports): it would span the space, not the queue, so dragging it (desktop thumb, iOS scroll indicator) lands on arbitrary positions and re-anchors under the pointer. Touch, wheel, trackpad and keyboard scrolling are unchanged. Desktop browsers with classic scrollbars also give the list back their gutter (15 px in Chromium on Linux).
  - **Scroll container:** `.queue-list` (`overflow-y: auto`), since the document never scrolls (see "Fixed viewport"), with `overscroll-behavior: contain` so its edge bounce doesn't chain to the page. Vertical panning stays allowed by the root `touch-action: pan-x pan-y`; don't set a narrower `touch-action` on it. Hidden in full mode by the queue area's `visibility: hidden`, never `display: none`, so it keeps its size and `scrollTop` and can be scrolled into place before the fade-in.
- **Blocks (`queue-store.ts`, `QueueStore`):** entries are cached in position blocks of 100 (`BLOCK`; block b holds positions 100b to 100b + 99, the last one shorter), tagged with the queue version they were read at. Each request is one block: `{"type":"queue","version","start":100b,"end":min(100b + 100, length)}`; a reply's block is `start / 100`.
  - **Wanted:** the blocks overlapping the visible rows plus two viewports above and below (`AHEAD_VIEWPORTS`, also the covers' range, see "Ahead of the view"), clamped to the queue; visible blocks first, then by distance from the viewport, ties below first.
  - **At most two in flight**, each counted until its reply (every valid request gets exactly one). Planning runs on each view report (every scroll pass reports the visible range), each reply and each show, and sends the nearest wanted block that is neither held nor in flight until two are out. So a fling queues nothing stale: each freed slot goes to whatever is nearest at that moment.
  - **Replies:** for the current version and a block within the kept range, stored. `[]` (MPD rejected the range: the queue shrank, a state push with the new version follows) marks the block empty for this version, not retried. `null` (not served) frees the slot and retries the block after 1 s. An older version is dropped, freeing the slot.
  - **Kept range:** blocks overlapping the visible rows ± 1,000 rows (10 blocks on each side); farther ones are dropped on each view report, so at most ~22 blocks (~2,200 entries) are held whatever the queue length or scroll distance.
  - **Version, offline, reconnects:** a state push with a new version keeps only the blocks overlapping the visible rows, as old rows (see "Auto-update"), and drops every other block and marker. `queue: null` (offline) drops everything. Every socket open frees all in-flight slots, since replies on an old socket never come (the visibility reconnect closes it without an offline snapshot), and keeps the blocks; the fresh snapshot's version decides whether they stay.
  - **Shown only:** requests go out only while mini mode is on and the page is visible. `App` calls `store.show(mini)` in a layout effect; a switch to mini centres the list (see "Auto-centre") and plans at once, so the current song's block goes first and loads during the 350 ms fade-in.
  - **Wiring:** `connect(onSnapshot, onConfig, store)`. The store implements `opened(send)` (on every socket open: the sender for window requests, slots freed), `state(queue)` (each snapshot's `queue`, before `onSnapshot`; `null` on close) and `reply(version, start, songs)` (parsed `queue` messages). `store.current` is `{ position, id }` from the last `state` (both `null` offline or with no current song); `store.shown` is the last `show`. The list subscribes with `subscribe({ stored(start, end), current(), opening(), hiding(), top(), recentre() })`: `stored` for each stored block, `current` when `state` changes the position or id, `opening` from `show(true)` before it plans, `hiding` from `show(false)` (a re-render pausing the rows' marquees), `top` from `store.top()` (after a playlist load, see "Stored playlists"), `recentre` from `store.recentre()` (cover tap, see "Auto-centre"). `stored` and `current` only mark the list and schedule its animation-frame pass (at most one per frame), so neither a reply nor a state push runs list work inside the WS message handler.
- **Auto-centre (`centre(position, viewportPx, length)` in `virtual.ts`):** puts the current row's centre at the viewport's centre: queue offset `position × 56 + 28 − viewportPx / 2`, clamped to `0 … length × 56 − viewportPx` (near the ends the first or last row sits flush; a queue shorter than the list stays at the top); anchor `clampAnchor(position − floor(spaceRows / 2))`, `scrollTop` = offset − anchor × 56, written in the layout effect like a re-anchor. No current song (`position` `null`): nothing moves.
  - **Opening:** every switch to mini centres and ends any pause; the place scrolled to before isn't kept. `opening` makes the list compute the placement, report the new view (so the store's first request is the current song's block) and re-render. `show` runs in `App`'s layout effect and Preact re-renders in a microtask, so the layout effect writing `scrollTop` runs before the first frame of the fade-in: the old position is never painted.
  - **Song change:** the pass after `current` re-centres if shown and not paused, else only re-renders (highlight). So now playing updates in the state push's render and the list follows within a frame. Instant, no smooth scroll (in random mode the next song can be anywhere in the queue). A new position with the same id (queue reordered) re-centres too. Hidden (full mode): no centring; opening does it.
  - **Pause:** user input on the list pauses auto-centring: passive `touchstart`, `wheel`, `pointerdown` with `pointerType` `mouse` (middle-click autoscroll) and `keydown`. Programmatic scrolls (centring, re-anchoring, the length clamp) fire `scroll` events too, so `scroll` alone never pauses. Each pausing input, and while paused every `scroll` event and `touchend` / `touchcancel`, restarts a 15 s timer (`RESUME_MS`); when it fires with no touch held, auto-centring resumes and re-centres (if shown); with a touch held it waits for the touch to end. A touch, wheel or momentum scroll always starts with a pause, so centring never sets `scrollTop` during one. Tapping a row ends the pause (see "Tap to play").
  - **Cover and album taps:** in mini mode, tapping now playing's cover or the album button (see "Queue actions") re-centres at once and ends any pause, like tapping the current row: `App` calls `store.recentre()` (the album button after sending), which reaches the list's `recentre` listener. For the album button the current song centres first, then the push's song change centres the album's first entry through the `current` pass, nothing being paused any more; if MPD rejects the command the list stays centred. Previous and next don't re-centre (user decision; a cover tap does it): the push's song change centres only when not paused, as for any song change. A fling still running would carry on from the centred spot: iOS doesn't stop momentum on a `scrollTop` write, so the list also gets `overflow-y: hidden` for two frames (one painted), which ends it. Chromium instead applies the fling's scroll deltas already in flight on top of the write, up to two frames late (~27 px each), which left the list off centre for good in 6 of 9 runs; so from the halt until the list settles (`SETTLE_MS`, no scroll for 150 ms), every pass re-centres unless the user paused it, undoing such a delta in the frame it lands. A row tap never comes during a fling (the touch stops it, no `click`), so there it changes nothing. No tap highlight on the cover; in full mode the cover tap doesn't touch the list.
- **Highlight:** the row whose entry `id` equals `store.current.id` gets `.current`: its texts (track number, title, artist · album, duration) in Gruvbox bright orange (`--bright-orange: #fe8019`, 5.9:1 on `bg0`; the bar's dark orange is 3.8:1, too low for small text), same size and weight, so nothing reflows. By id, not position, so it stays right while old rows are still shown across a version change (see "Auto-update"). A row not loaded yet has nothing to highlight.
- **Auto-update (`queue-store.ts`):** a new queue version (another client adding, deleting, moving or shuffling, a database update changing tags, loading a stored playlist) keeps the visible rows' old entries on screen until their replacement arrives: no blank flash.
  - **Blocks carry their version.** On a state push with a new version, the blocks overlapping the last reported visible rows stay, with their old version; every other block, every `[]` marker and every retry timer is dropped, and if any block went, `stored(0, Infinity)` makes the list re-render (margin rows outside the viewport go blank). Several versions in a row before the refetch lands: old blocks overlapping the view stay whatever their age.
  - **Only current-version blocks count as held**, so planning refetches the old visible blocks first, like missing ones (they are visible), at most two in flight as always. A current-version reply replaces the old block and announces it (`stored`): the rows change text in place. `[]` replaces it too (rows blank; the shrink's own state push follows); `null` keeps the old entries shown and retries after 1 s. Old blocks leave the kept range like any other.
  - **Rows past the new length go at once:** `entry(position)` returns `undefined` from the queue length on, and the list renders only `length` rows (its length prop changes with the push).
  - **Position-stable:** rows inserted or removed above the view shift the songs under it; the list keeps the queue position at the viewport's top (`resize`), not the songs shown. Finding where shown songs moved would take a `plchangesposid` round trip per change. While auto-centring, the current song's new position re-centres anyway (`current`).
  - Hidden (full mode): the same rule, with the last view reported while shown; nothing is requested until the next opening, which centres and requests as usual.
  - The list has no auto-update logic of its own: highlight by id stays right on old rows, and the list re-renders on `stored`.
  - Replacing the whole queue takes the same path: `replace_queue`'s command list reaches other connections as one `playlist` event with the new length (see "Queue measurements"). A push showing an empty queue in between would empty the list (length 0).
- **Rows:** two lines inside the 56 px row, padded 20 px left and right like the now-playing section: a 40 px left column for the track number, under the album's cover (see "Album grouping" and "Covers"), then, from x = 72 px, the title (`0.9375rem` / `1.25rem`) above artist and album joined by `·` (either alone when the other is missing; `0.8125rem` / `1.125rem`, muted), each one marquee line (the shared `Marquee`, so too-long text bounces like now playing's instead of ending in an ellipsis; user decision); the duration on the right, vertically centred (`0.8125rem`, muted, tabular, `formatTime`, empty when `null`). Every row always has the same four cells, empty until loaded, so filling a row only changes text. The design is settled for now (user decision).
  - **Stripes:** rows at odd queue positions (the 2nd, 4th… row) get `.odd`, a `bg0_s` (`--bg-soft: #32302f`) background, the next gruvbox step from `bg0`, so adjacent rows read apart without hard lines. By position, not pool slot, so a song keeps its shade across re-anchors and pool size changes; empty rows are striped too, so loading changes no shade. Text contrast on `bg0_s` stays above 4.5:1: `fg1` 9.6:1, muted `fg4` 4.7:1, bright orange 5.2:1; the separator (`bg2`, 1.5:1) stays visible on either shade.
- **Album grouping:** adjacent entries with the same album form a group; the group's first row gets a separator. Rows keep their 56 px, so offsets never change. The rule exists once, on the server (`same_group` in `bridge.rs`), so the list's separators and covers and anything else grouping the queue (the album button) agree by construction.
  - **Same group:** `album` equal and not `null`, and `folder` equal, on the converted entries. Same folder keeps apart two adjacent albums of the same name ("Greatest Hits"); `album` falls back to the folder name, so untagged folders group too. Streams and files at the top of the music directory (`album` `null`) are a group each. Without `--music-url`, `folder` is always `null` and grouping is by album name alone.
  - **Group start:** position 0, or an entry not in the same group as the one before it: each entry's `start` flag, computed by the server per window (see "Windows"). `store.starts(position)`: the flag, or `undefined` while the entry isn't served (not loaded, past the length). Every block carries its own flags: no wait for the previous block, and no mix of versions across a version change.
  - **Separator:** group-start rows other than position 0 get `.group`: a 1 px line in `--track` (`bg2`) across the row's top edge, inset 20 px like the text, drawn by `::before` (absolutely positioned) so nothing reflows. It appears with the row's text, in the same render.
  - **Track number:** in the left column on every row, grouped or not, spanning both lines and centred: muted, `0.8125rem`, tabular; empty when `null` or not loaded. Four digits fit (game soundtracks: 244 of 7,000 entries sampled across the real queue; three digits 699, none 403). The album's cover hides the one it passes over (see "Covers").
- **Covers:** each group's cover sits over the left column of its rows, drawn above them: on the group's first row while that row is in view, then pinned 8 px below the list's top while the rest of the group scrolls under it, until the group's last row pushes it off. So a group shows its cover once, beside its top visible row, and where every row is its own group every row has its cover. Track numbers stay on every row; the cover hides the one it passes over, a number scrolling under the pinned cover shows above it until hidden, and a non-square cover's letterbox bands show what's under them (user decision). A group without a cover shows only its track numbers: no placeholder in the list (user decision).
  - **Pinning (`position: sticky`):** each group with a found cover gets a `.queue-album` box over the track column (x 20–60 px) spanning its rendered rows, the cover inside it at `position: sticky; top: 8px`, 40 × 40 px, scaled to fit and centred (`object-fit: contain`, like now playing). A sticky element stays within its parent's content box; the box's 8 px padding above and below is the cover's inset in a 56 px row, so the cover rests exactly on its first and last rows' places. The browser keeps it in place as part of scrolling, so no script runs per frame; positions set from `scroll` events would trail the rows by a frame on iOS, where momentum scrolling runs outside the page's thread.
  - **Spans (`albumSpans` in `virtual.ts`):** the groups among the pool's rows, from `store.starts`: each runs from a group start, from the pool's first row (a group started above) or after rows not served, to the next group start or row not served. The pool reaches 15 rows past each edge of the list, so a box ends on screen only where its group does; later rows not loaded yet end it early until they arrive. Boxes are placed with `top` and `height` from `(start − anchor) × 56`, like the rows, so a re-anchor moves them in the same render and nothing moves on screen. Recomputed on every render (first rendered row changed, entries or covers arrived), never per frame.
  - **Elements:** one `<img alt="" decoding="async">` per box, the boxes after the rows in a wrapper with `aria-hidden`, `pointer-events: none` so taps reach the row below. Keyed by folder and album (plus a count for an album found twice in the pool), so a box keeps its element while its span changes, also when its group start leaves the pool while the cover is pinned. A box is created when its group's first row enters the pool and removed when its last row leaves it, both off screen, except on jumps (opening, centring, a queue change) and when a cover arrives for a group in view. Rows without a `folder` (no `--music-url`, streams) have no cover.
  - **States:** a group gets its box once its folder's cover is found; a miss (or a folder not probed yet, or probing) adds nothing, so nothing changes on a miss. A known result renders in the same frame as the rows' text, so scrolling back over seen groups shows their covers at once.
  - **Probing:** through `cover.ts`, sharing its per-folder results with now playing, so the current song's group costs nothing extra and vice versa. `findCover` returns the in-flight promise for a folder already being probed, so the list and now playing never probe the same folder twice. Shown only: nothing is probed for the list in full mode.
  - **Ahead of the view:** a probe downloads and decodes the image, so the list probes around the view, during scrolling, without waiting for it to stop, and covers are already loaded when their rows scroll in:
    - **Range:** the folders whose result is unknown among the visible rows plus two list heights above and two below (`AHEAD_VIEWPORTS`; five screens, ±21 rows at 580 px). A group's rows share its folder, so this covers every group touching the range, also one started above it (centred mid-album, its cover shows). The store's wanted blocks span the same range, so its entries (text included) and so its group starts and folders are loaded ahead too. Rows past the pool's 15-row margin have no box yet: their probe fills the HTTP cache, and their cover loads from it once they enter the pool, 15 rows before they're visible.
    - **When:** on every animation-frame pass (scrolling, blocks arriving, a probe finishing, a song change), resize and opening. Centring (opening, song change, tap) is a jump, not scrolling: it clears the speed samples, so its pass probes.
    - **Too fast:** no new probes while the list moves faster than 100 rows/s (`AHEAD_ROWS_PER_S`; 5,600 px/s, ~10 lists/s), measured on the queue offset (anchor × 56 + `scrollTop`) since the oldest pass of the last 100 ms (`SPEED_MS`; after a pause, the previous pass counts as 100 ms ago, so a single jump is judged by its size). Below it a row probed two lists ahead is ≥ 200 ms away, longer than most covers take (now playing measured 38–216 ms); above it rows cross the list in under 100 ms. Probing resumes in the first slower pass, or once no pass ran for 50 ms (`STOPPED_MS`: scrolling runs a pass every frame, so the list stopped). A hard fling starts above it and decays below it within a few hundred ms, so covers load during its tail; if they ever pop in after hard flings, raise it.
    - **Order and cap:** at most 12 list probes in flight (`AHEAD_PROBES`, a full 580 px viewport of groups, so the visible ones never wait), counted per folder until `findCover` resolves; each probe call starts new ones while slots are free: the visible rows' folders first (top to bottom), then the range on the scroll's side nearest first, then the other side nearest first (below first before any movement). Like blocks, a fling queues nothing stale: each finished probe schedules a pass, and the free slot goes to what's nearest then. A started probe runs to completion; its result is kept for the session.
    - **Cost:** each folder once per session; only around the shown list, nothing in full mode. Per stop in a fresh region, 2–14 probes (0.2–10 MB) in typical parts of the real queue, 41–44 (misses, ~0 MB) where every row is a different folder (see "Measurements" → "Covers ahead of the view"); plus the folders passed while scrolling below the limit.
  - **Arrival:** a finished probe schedules the animation-frame pass (to fill its slot), and a found cover also marks the list stale, so any number resolving in one frame cost one render; a miss renders nothing (the track number stays). Results for folders no longer rendered are kept, not shown.
  - **Image sizes** (71 covers of 88 folders sampled across the real queue; 60 `cover.jpg`, 11 `cover.png`): median 157 KB and 600 px on the long side, 75th percentile 341 KB / 1024 px, 90th 1.7 MB / 1,521 px, largest 5 MB / 3,000 px (13–14 MB outliers exist). The mirror's full images are used as they are, downloaded once and shared with now playing and the browser cache; thumbnails would need the server to fetch and resize them (a server hop, against the decision under "Server"), and the iPhone shows no cost from the full images.
- **Tap to play:** tapping a loaded row plays it: `{"type":"playid","id"}` with the row's entry id, on the command connection (`Command::PlayId { id: u32 }` → `Client::play_id`; dropped while offline like any command). By id, not position, so a row still showing an old version (see "Auto-update") plays the song it shows, or nothing if that song left the queue (MPD's `ACK`, logged). No optimistic UI: now playing and the highlight move with the state push.
  - **Tap, not scroll:** one delegated `click` listener on the list, not one per row; the row from `closest(".queue-row")`, its position from `aria-posinset`, the id from `store.entry`. Browsers fire no `click` for a touch that scrolls or that stops a fling, so swipes and momentum stops never play. No 300 ms delay: the root's `touch-action: pan-x pan-y` already rules out double-tap zoom. A row not loaded yet (no entry) does nothing. Mouse clicks play too; middle-click is `auxclick`, not `click`. `App`'s `send` is created once (`useState`), so passing it keeps the list's memo.
  - **Current row:** tapping the current song's row sends nothing (`playid` would restart it from the beginning); it only centres.
  - **Centring:** the tap ends the pause its own `touchstart` began (`paused` false, resume timer cleared), so the list follows the current song again: the `current` pass after the push centres the tapped row, instantly like any song change, 3–240 ms after the tap (MPD opening the file). The current row is centred at once, since no push comes. If MPD rejects the id nothing moves, and the next song change centres.
  - **Feedback:** only the highlight. No `:active` style: a touch can't be told from a scroll at `touchstart`, so it would flash on every scroll. `-webkit-tap-highlight-color: transparent` on the list, or iOS flashes the whole list (the listener's element) grey on every tap.
- **Offline:** the list is empty (no length) and the store drops every block; refetched after reconnecting.

### Measurements

Headless Chromium (390×844, touch emulation for the queue) against the local MPD unless noted; the queue ones against its real queue (175,872 entries, random on), with `--music-url` for covers. Each was taken when its feature landed, "previous" being the build before it; measurements a later change made obsolete are removed.

**Now playing**, timed from the action to the DOM change: `mpc` pause/play/seek/next/prev 2–4 ms; button toggle/next/previous 2 ms. The bar advances every frame (62 samples/s, monotonic) and holds still while paused. Killing the proxy or the server shows offline with disabled buttons; after a server restart the UI recovers within the 1 s retry (353 ms observed). After freezing the page (Chrome closed the socket) and seeking meanwhile, the visibility event opened one new socket and the bar matched MPD within 3 ms.
