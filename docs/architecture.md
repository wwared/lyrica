# Architecture

```
iPhone (PWA) ──HTTPS/WSS── Caddy ──HTTP/WS── lyrica (crates/lyrica) ──TCP── MPD
                                               │  embeds web/ build
                                               └─ uses lyrica-mpd (crates/mpd)
```

Only the general direction is fixed here; details are decided while implementing and recorded back into this file.

## `lyrica-mpd` (crates/mpd)

Async MPD client library, independent of the web server.

- tokio TCP connections; responses parsed with nom 8 (`Parser` trait API).
- Implements only the commands lyrica needs, added incrementally. Currently: `password`, `ping`, `status`, `currentsong`, `playlistinfo START:END`, `play`, `playid`, `pause`, `previous`, `next`, `random`, `repeat`, `single`, `setvol`, `seekcur`, `idle`.
- **`Client`** is one connection running one command at a time; responses are framed by line and each line parsed with nom (`OK`, `ACK …`, `key: value`). Typed results (`Status`, `Song`) keep only the fields lyrica uses or is about to use and ignore unknown keys. Multi-song responses (`playlistinfo`) start a new `Song` at each `file` line. `Track` is kept as a number, `None` when it isn't one, so an odd tag never fails a window (MPD reported plain numbers for all 5,000 sampled entries, 2,231 of them with the tag twice).
  - **Queue ranges** (`queue_range`): MPD clamps the end to the queue length and returns nothing for an empty range; a start past the queue's end, or after the range's end, is an `ACK`.
  - **Reads:** `TCP_QUICKACK` is re-armed before every socket read (Linux; `socket2`), see "Socket options" below. Lines are read into their own buffer, then appended to the response: tokio's `read_line` re-validates the UTF-8 of its whole buffer on each call, which made a 100-entry window take 3.1 ms instead of 0.43 and a 200-entry one 10 ms.
  - `ACK` errors leave the connection usable. I/O and protocol errors, or a command future dropped mid-response, leave it out of sync: later commands fail with `Error::Broken` and the caller reconnects.
  - `idle` blocks its connection, so idling needs its own `Client`. Arguments are always quoted; newlines are rejected.
  - Not yet handled: MPD's `connection_timeout` closing unused connections, binary responses, command lists.
- **Connection multiplexing:** slow work must never delay interactive work. The server uses one connection idling for state changes and one for commands (see "MPD bridge"); queue windows get a third (planned, "Queue" below), later shared by stored playlist listings, so neither state updates nor commands ever queue behind them.
- Large results (queue, playlists) are always requested in ranges/windows, never wholesale. MPD serves all its clients from one event loop, so a large response delays the other connections too; queue windows stay around 100 entries, under 1 ms of MPD time (see "Queue measurements").

## Server (crates/lyrica)

Thin bridge between the frontend and `lyrica-mpd`.

- axum on tokio; serves the embedded frontend (rust-embed) and the frontend WebSocket at `ws` (relative to the page).
- Configuration via CLI arguments (clap), plus `LYRICA_MPD_PASSWORD` for the password; no disk state.
- Plain HTTP; intended to sit behind Caddy. All frontend URLs are relative so a path prefix works, provided the page URL ends in `/`.
- Setup-specific extensions live here or in `lyrica-mpd` as appropriate, e.g. album art from the HTTP mirror of the music library. Decided: the browser loads art directly from the mirror (no server hop, browser caching, no server bandwidth); the server only supplies the folder URL. Art is only ever looked for in the song's own folder (user decision). Same for MPD's `httpd` audio stream: the browser plays it directly from `--stream-url`.

### MPD bridge (`bridge.rs`, `ws.rs`)

- **CLI:** `--listen` (default `127.0.0.1:8080`), `--log` (`EnvFilter` syntax, default `info`). `--mpd <host:port>` (default `127.0.0.1:6600`), optional `--mpd-password` (or `LYRICA_MPD_PASSWORD`, which keeps it out of the process list), sent with `password` after every connect. Optional `--music-url <URL>`: base URL of the HTTP mirror of MPD's music directory (e.g. `https://webmusic.wwared.com/`; a missing trailing `/` is added); without it `folder` is always `null` and no art is shown. Optional `--stream-url <URL>`: MPD's `httpd` output (must be HTTPS when the page is, or it is blocked as mixed content); without it there is no play-here toggle.
- **Idle connection:** a task owns one `Client`. It fetches `status` + `currentsong`, publishes the snapshot, then loops `idle(player, options, mixer)` → refetch → publish. Snapshot fetches run on this connection, so they never queue behind commands.
- **Command connection:** a task owns a second `Client` and serves an `mpsc` of commands from all WS clients, serialized. MPD closes connections unused for `connection_timeout` (default 60 s), so on `Io`/`Broken` it reconnects and retries the command once; the closed connection never executed it. `Ack` is logged, not retried.
- **Snapshot fan-out:** `tokio::sync::watch`. Each WS client gets the current snapshot on connect, then every change. While playing, `elapsed` is advanced to the send time, so late subscribers get the current position.
- **MPD unreachable:** the idle task publishes an `offline` snapshot and reconnects with backoff (1 s doubling to 10 s). Commands sent while offline are dropped with a log line.
- **WS protocol:** JSON text messages (serde). Revisit only if size or speed proves a problem.
  - Server → client, first on every connection: `{"type":"config","stream":string|null}`, `stream` being `--stream-url` verbatim.
  - Server → client: `{"type":"state","state":"play"|"pause"|"stop"|"offline","title":string|null,"artist":string|null,"album":string|null,"folder":string|null,"elapsed":number|null,"duration":number|null,"volume":number|null,"random":bool,"repeat":bool,"single":bool}`. `title` is the `Title` tag, falling back to the file name; `null` when there is no current song. `artist` is the first `Artist` tag, falling back to the first `AlbumArtist`; `album` the first `Album` tag, falling back to the name of the file's folder (none for streams or files at the top of the music directory); `null` when missing. `folder` is `--music-url` plus the song's directory with each path segment percent-encoded (RFC 3986 unreserved characters kept), ending in `/`; `null` without `--music-url`, without a song, or for streams (`file` containing `://`). `folder` and the `AlbumArtist` and folder-name fallbacks come from the `currentsong` response already fetched, so they cost no extra MPD round trip. `elapsed`/`duration` are seconds (fractional) from `status`. `volume` is MPD's volume (0–100) from `status`, `null` when MPD reports none (no mixer, or none open: the local MPD, its output disabled, has none); the bridge also idles on `mixer`, so other clients' volume changes are pushed. `random`/`repeat`/`single` are the modes from `status` (`false` while offline); `single` is also `true` for MPD's `oneshot`. Consume is deliberately absent (unused).
  - Client → server: `{"type":"previous"}`, `{"type":"toggle"}`, `{"type":"next"}`, `{"type":"random"}`, `{"type":"repeat"}`, `{"type":"single"}`, `{"type":"volume","volume":0–100}` (`setvol`, MPD's global volume, like `mpc volume`; MPD rejects more than 100 and the rejection is logged), `{"type":"seek","position":seconds}` (`seekcur`, absolute, millisecond precision; negative or out-of-range positions are invalid; MPD rejects it while stopped). Invalid messages are logged and ignored.
  - No per-command replies: the state push triggered by `idle` is the confirmation. Measured on the local MPD (WS client to state message): `toggle` 0.4–1.8 ms, `next` 19 ms, `previous` 3 ms; via `mpc` (including process spawn): `pause` 1.5 ms, `play` 40 ms, `seek` 8 ms. After killing the proxy, `offline` arrives in 40 ms; the first command after a lost connection or a 65 s idle gap reconnects and succeeds in < 2 ms. MPD does not time out connections in `idle`.
- **Toggles** are mapped by the server from the latest snapshot. `toggle`: `play` → `pause(true)`, `pause` → `pause(false)`, `stop` → `play()`. `random`/`repeat`: set to the opposite of the current mode. `single`: on (including `oneshot`) → `single 0`, off → `single 1`. Never send a command that changes nothing: MPD emits no idle event for it, so the frontend would get no update.
- **Queue (planned, roadmap "Live queue"):**
  - **State fields:** the state message gains `"queue":{"version":n,"length":n,"position":n,"id":n}` from the `status` already fetched (`playlist`, `playlistlength`, `song`, `songid`); `position` and `id` are the current song's, `null` when there is none, and `queue` is `null` while offline. The idle loop also waits on the queue subsystem (MPD's `playlist`), so a queue change pushes a new state like any other change. Queue entries never travel in the state message.
  - **Queue connection:** a third `Client`, owned by a task serving window requests from all WS clients over an `mpsc`, one at a time, with the command connection's reconnect-and-retry-once rule. Never the idle or command connection, so state pushes and commands never wait on queue reads.
  - **Socket options:** every MPD `Client` sets `TCP_QUICKACK` before each read (Linux resets it), avoiding the 40 ms stalls (see "Queue measurements"); done in `lyrica-mpd`. Over the VPN a segment holds ~1.4 KB instead of loopback's 64 KB, so even a tag-heavy `currentsong` on the idle connection can span segments; the cost is one `setsockopt` per read. Accepted HTTP / WS connections get `TCP_NODELAY` (axum doesn't set it): with Nagle, a state push sent right after a window reply would wait for the proxy's delayed ACK, the same 40 ms on the path that must stay instant. `TCP_QUICKACK` doesn't help there: it only changes our ACKs for what we receive, a few tiny commands.
  - **Windows:** client → `{"type":"queue","version":n,"start":n,"end":n}` (positions, `end` exclusive; the server refuses more than a few hundred entries, so nothing can request the whole queue); server → `{"type":"queue","version":n,"start":n,"songs":[…]}`, `version` echoed unread. Per entry only what the list shows: `id`, `title`, `artist`, `album`, `track`, `duration`, `folder`, with the state message's fallbacks. MPD sends every tag (300–1100 B per entry here); the server forwards a fraction of that.
  - **Consistency without locking:** the client tags each request with the version it has and drops replies for an older one. A window read just after a queue change, before its state push arrives, is stored under the old version and dropped when the push lands: at worst a refetch, never stale rows shown as current.
  - **The WS loop never waits on the queue:** requests are handed to the queue task with `try_send` on a bounded channel (the client caps its requests in flight below the capacity, so it never fills), replies come back on a per-connection channel, and the loop's `select!` is `biased` toward state changes, so a pending window reply never delays a state push. Replies are small (~100 entries, a few tens of KB).
- **Queue measurements** (local MPD 0.24, 175,872-entry queue, raw TCP client): `status` 0.09 ms. `playlistinfo` of 100 entries 0.4–0.7 ms and 31–114 KB, 300 entries 1.2 ms / 180 KB, 1000 entries 4.5 ms / 654 KB; the whole queue 132 MB in 10.7 s. `plchangesposid` for the current version: empty, 0.24 ms.
  - **~40 ms stalls from delayed ACKs:** in runs of 20 windows, 7–18 of the 25-, 50- and 100-entry ones took 40–43 ms, none of the 10- or 200-entry ones, with or without `TCP_NODELAY` on the client. Setting `TCP_QUICKACK` before every read removed all of them (25 / 50 / 100 entries: 0 of 20 stalled, medians 0.09 / 0.15 / 0.24 ms). So MPD holds the last segment of a response until our ACK arrives, which Linux delays by 40 ms; not storage (`playlistinfo` is served from memory). Responses within one segment never stall.
  - **`lyrica-mpd` client** (release build, 40 windows per size spread over the queue, two runs): medians 0.07 / 0.13 / 0.23 / 0.43 / 0.82 ms for 10 / 25 / 50 / 100 / 200 entries, maximum 1.3 ms, no stalls; `status` and `currentsong` 0.02–0.03 ms. With the `TCP_QUICKACK` line disabled: 25 / 39 / 28 of 40 windows of 25 / 50 / 100 entries and 2 of 40 of 200 took 41–42 ms; 10 entries never.

## Frontend (web/)

Preact + TypeScript PWA built by Vite into `web/dist`, which is embedded into the server binary.

UI direction (implemented parts are detailed under "Now playing"; the rest is planned, see `roadmap.md`):

- **Now playing, pinned to the bottom:** album art, title, artist, album, progress bar with the time beside it, then controls at the very bottom (previous, play/pause, next, with the play-here and volume toggles on the left and random/single/repeat toggles on the right). Every element has a fixed height so nothing moves when the song changes.
- **Two modes, switched by a chevron:** full (large art above the title) and mini (art left of title/artist/album/progress/transport; above it, the toolbar and the queue). Always opens in full mode; the switch is animated, smooth and unflashy.
- **Progress bar:** updates smoothly and continuously during playback. Each `state` message anchors `elapsed` to the local receive time (`performance.now()`); while `play`, the bar shows `elapsed + (now − anchor)`, clamped to `duration`, redrawn every animation frame. Re-anchored by every state push (seek, pause, song change) and by the fresh snapshot after a reconnect. No polling.
- **Seeking:** tap or drag on the progress bar, full mode only (in mini the bar is too small to use comfortably).
- **Mini mode, top to bottom:** toolbar, live queue, mini player. All three keep fixed positions; only the queue scrolls.
  - **Toolbar (planned):** a fixed-height row (44 px) below the safe-area top, holding the stored playlists button and later the queue actions. Empty at first, with its height reserved, so the queue's geometry never changes when buttons arrive. Toolbar and list make up the queue area (`.queue`), which already fades in with mini mode and has one geometry in both modes.
- **Live queue (planned; the queue area is a placeholder now):** the current MPD queue, read-only: no reordering, adding, removing or consume mode.
  - **Hard requirement: no regression in responsiveness.** Now-playing updates, controls, the mode switch and scrolling stay exactly as fast as without the queue. Every queue operation, server and client, runs in the background, on demand and in small pieces:
    - **Shown:** while the queue is shown (mini mode, page visible), blocks load on demand as described under "Blocks".
    - **Hidden, background preloading (conditional):** in full mode, the blocks around the current song are kept loaded and current (song changes, new queue versions), and their groups' covers probed, so switching to mini shows a filled list at once. Low priority: one request at a time, started only when the page is idle (`requestIdleCallback`, a timeout where unsupported, as in Safari). Kept only if the checks below show no measurable impact; otherwise removed, and the queue and its covers load only while shown.
    - Queue data lives in its own store, fed by `ws.ts` directly (queue messages bypass `App`'s snapshot state). The list component gets only queue version, length, current position / id and `mini`, memoized, so state pushes that change anything else (elapsed, volume, modes) don't re-render it, and a song change re-renders only the old and new highlighted rows.
    - Scrolling: a passive listener, work batched to one pass per animation frame, a re-render only when the rendered range changes; rows positioned with `transform`, no layout reads in loops.
    - Server side: the queue connection and the non-blocking WS loop (see "MPD bridge" → "Queue").
    - Every step is checked in headless Chromium against the real queue: `mpc` play/pause/next to DOM stays within today's 2–4 ms while the list loads and scrolls, no long tasks (> 50 ms) during a fling, the mode switch keeps every frame.
  - **Virtual list over a bounded scroll space:** only the rows in view plus a margin (~30) exist in the DOM, recycled by slot (position modulo the pool size), so scrolling and refreshes rewrite existing rows instead of creating and destroying them. A fixed row height makes position ↔ offset plain arithmetic. Rows not loaded yet are empty rows of the same height, filled in place: no spinner, nothing moves.
    - The scrolled content is not length × row height: browsers cap element heights (~33.5 M px in Chrome and WebKit, ~17.9 M px in Firefox, ~300k rows at 56 px). It is a fixed scroll space (~1 M px, ~18k rows) mapped onto the queue through an anchor: queue offset = anchor + `scrollTop`. So the queue length is unbounded.
    - When scrolling stops (no `scroll` event for ~150 ms and no touch held), the anchor moves so the viewport sits mid-space again; anchor and `scrollTop` are written in the same frame, so nothing moves on screen. Re-anchoring waits for scrolling to stop because setting `scrollTop` cancels momentum scrolling (iOS); half the space (~9k rows) is far more than one fling covers, to be confirmed on an iPhone.
    - Near the queue's ends the space is clamped to them, so its edges are the real start and end, bounce included. Auto-centring is a re-anchor around the current song.
    - Cost: the scrollbar shows the position within the space, not within the whole queue.
  - **Blocks:** entries are cached in fixed-size position blocks (~100). Blocks covering the viewport and about one viewport beyond it in both directions are requested, at most two in flight; when one returns, the still-needed block nearest the viewport goes next, so a fling never queues stale requests. Blocks far from the viewport are dropped, so memory stays bounded whatever the queue length. Replies for an older queue version are dropped.
  - **Auto-centre:** opens centred on the current song (scroll position set before the fade-in, its block requested first, hidden behind the 350 ms switch) and re-centres when the song changes. Scrolling by the user pauses it; 15 s after scrolling stops it resumes and re-centres. User scrolling is detected from touch, wheel and pointer input, since programmatic scrolls fire `scroll` events too; the scroll position is never set during a touch or momentum scroll.
  - **Highlight:** the current song's row (by `songid`) in an accent colour.
  - **Auto-update:** a new queue version drops blocks outside the view and refetches the visible ones, keeping the old rows shown until their replacement arrives (no blank flash); rows past the new length go at once. Replacing the whole queue (loading a stored playlist) takes the same path.
  - Its own scroll container (`overflow-y: auto`), since the document never scrolls (see "Fixed viewport"), with `overscroll-behavior: contain` so its edge bounce doesn't chain to the page. Vertical panning stays allowed by the root `touch-action: pan-x pan-y`; don't set a narrower `touch-action` on it.
  - **Album grouping:** adjacent entries with the same folder and album form a group with a small separator inside the row (fixed heights, so offsets never change). A block's first row needs the previous block's last entry to know whether it starts a group.
  - **Cover per group:** one per group, from the HTTP mirror via `cover.ts` and its per-folder cache, shared with now playing; probed only for groups visible once scrolling settles, so a fling starts no probes (plus the preloaded groups, if preloading stays). No cover if the album has none.
  - Per-track info: album, album/track artist, title, track number, duration. Exact layout to be iterated on.
  - **Tap to play:** `playid` on the command connection; the highlight moves with the state push (no optimistic UI).
  - **Offline:** the list is empty (no length); refetched after reconnecting.
- **Stored playlists (planned):** a button in the toolbar opens the list of server playlists; tapping one clears the queue and loads it. The only way lyrica changes the queue. No general settings menu.
- **Queue actions (later, to design):** convenience buttons in the toolbar, e.g. play the current album from its first track with random off.
- Slow data (cover art, queue windows, playlist listings) is fetched lazily and asynchronously; controls and now playing never wait on it.
- Dark only: one scheme whatever the system preference (`color-scheme: dark`, so form controls and scrollbars match). Gruvbox dark, from CSS variables: background `bg0`, foreground `fg1`, muted `fg4`, bar track and pressed buttons `bg2`; `theme-color` and the manifest colours repeat `bg0`. Accents: dark orange (`#d65d0e`) for the progress and volume fill; bright yellow for the open volume toggle; when on, random is aqua, single blue, repeat purple and play here green (bright). Transport buttons stay `fg1`, toggles that are off `fg4`.
- **PWA:** installable (manifest, standalone display, iOS meta tags), named "Lyrica" (page title, manifest, home-screen title). Icons in `web/public/` are generated from `web/icons/lyrica.png` (see `development.md`): 192 and 512 px for the manifest, also listed as `maskable` since the artwork is full-bleed (Android crops its edges instead of shrinking it onto a white disc), 180 px `apple-touch-icon`, 32 px favicon with rounded corners. The manifest asks for portrait (`orientation`), honoured by installed Android apps; iOS ignores it and can't lock orientation from the web (`screen.orientation.lock` is behind a flag and needs fullscreen, WebKit bug 257695). No service worker: the app needs the server and MPD to do anything, so offline launch is useless. Chrome on Android installs without one (since 108), but needs the icons and HTTPS.

### Now playing (implemented)

Covers album art, title, artist, album, play state, progress bar and seeking on it, previous / play-pause / next, random / single / repeat, MPD's volume, playing the `httpd` stream here, and the full / mini mode switch.

- **`ws.ts`:** owns the socket and the protocol types (`Config`; `Snapshot`: a `state` message stamped with its `performance.now()` receive time; `Command`). Parses `config` and `state` messages (ignores anything else), exposes `send(command)` (dropped unless open). Reconnects 1 s after a close. On `visibilitychange` to visible, closes and reopens the socket: the server sends a fresh snapshot on connect (with `elapsed` advanced), which resyncs the bar and avoids zombie sockets after iOS suspends the page; `performance.now()` may not advance while the device sleeps.
- **Offline:** a closed socket is displayed exactly like `state: "offline"`. Buttons are disabled while offline, except the play-here and volume toggles (the volume slider is disabled).
- **No optimistic UI:** buttons only send; the UI changes when the state push arrives (< 20 ms on the local MPD).
- **Play/pause button** shows pause while `play`, play otherwise; sends `toggle`.
- **Control strip:** a three-column grid (`minmax(0, 1fr) auto minmax(0, 1fr)`), so previous / play-pause / next stay centred, with the play-here and volume toggles (`.extras`, 44×44 px each, the first icon lined up with the start of the progress bar) left-aligned in the first column and the mode toggles right-aligned in the third, without shifting them. Transport buttons are 52×56 px; the toggles (random, single, repeat; Material Icons shuffle, looks_one, repeat) are 26×44 px so all three fit beside the centred transport down to 375 px wide screens; at 375 px the volume toggle ends 3.5 px before previous. Off: muted colour; on: foreground colour (`aria-pressed`, `aria-expanded`). Each mode toggle sends its mode command; the state push updates it. In mini mode the strip is the column right of the art: the transport is centred there with 48 px buttons and no gaps (fits 147 px at 375 px) and the play-here, volume and mode toggles are hidden (user decision: there is no room for them beside a full-height art).
- **Volume (`volume.tsx`):** the toggle (Material Icons volume_up, always shown; no level on it) opens a pill that grows right from it (200 ms `clip-path` reveal) over the rest of the control strip: 44 px tall, rounded, bordered, opaque, from the toggle's left edge to the strip's end (capped at 360 px wide on large screens). The toggle stays on top inside the pill's left end, in the "on" colour, so the pill reads as its slider; then the bar and the level (fixed 3-character box, `–` when `volume` is `null`, then without a thumb). Title, artist, album and progress stay visible. Closed again by the toggle or by switching to mini mode. Sets MPD's global volume, not the stream's (MPD applies it to the stream itself).
  - **Input:** pointer events with capture on the slider part of the pill (its full height, so tap or drag anywhere sets the value from the x position; `touch-action: none`), not `<input type="range">`, whose iOS version only follows drags that start on the thumb. Keyboard: `role="slider"`, arrows ±5, Home / End.
  - **Throttled, then held:** a change shows at once and is sent at most every 100 ms while dragging, the last value always. The local value stays shown for 1 s after the last change, so state pushes for the intermediate values sent meanwhile don't make the thumb jump back; then the bar follows `volume` again (including other clients' changes). Values equal to the shown one aren't sent.
- **Play here (`stream.ts`):** a toggle (Material Icons headphones), shown only when `config.stream` is set; off/on colours as the mode toggles. Plays MPD's `httpd` output (an endless, real-time Ogg Opus stream) through a detached `Audio`, so the page has no native audio controls. Local state, not persisted; always starts off.
  - **Live, never paused:** on sets `src` and calls `play()` in the click handler itself (iOS only allows `play()` within a gesture); off removes `src` and calls `load()`, which aborts the request. So every on is a new connection that joins the stream at the current point, never a resume from a stale buffer. A `pause` the page didn't cause (iOS lock screen or Control Center, headphones unplugged, a call) turns it off for the same reason; Media Session `play` / `pause` / `stop` handlers map the lock-screen buttons to on / off.
  - **Reconnects while on:** `error` or `ended` (MPD stops and closes the output, the network drops) loads the stream again after 1 s, indefinitely. If `play()` is refused (`NotAllowedError`: a retry without a gesture, e.g. in the background on iOS), it turns off.
  - **Lock screen / Control Center:** Media Session metadata mirrors the page: title (the heading, so also "Offline" etc.), artist, album, and the cover as artwork (absolute URL; the placeholder when there is none; left out while the cover is unknown, so the placeholder never flashes in). Set on every change and again on each `playing`, in case the browser dropped metadata set while nothing played. The cover comes from `useCover` in `app.tsx`, shared with the art, so it costs no extra requests.
  - **Latency:** no buffering of our own and no catch-up: playback starts as soon as the browser can (`canplay`), and the browser picks its buffer, which `<audio>` gives no control over. Seeking or reloading to cut latency would skip audio (user decision: some latency over skips). Stalls (the stream arrives in bursts) grow the buffer, so latency can drift up during a session; toggling off and on resets it.
  - **iOS:** background and lock-screen playback works in home-screen apps since iOS 15.4 with `<audio>` (not Web Audio, which iOS suspends in the background); Ogg Opus needs iOS 18.4. Setting `src` before every `play()` also avoids iOS 26 home-screen apps playing silence after a relaunch (WebKit bug 295518). A home-screen app left paused in the background for ~30 s can't be resumed from the lock screen until it is opened again (accepted by the user).
- **Album art:** a square, always present so nothing jumps; the image is scaled to fit and centred (`object-fit: contain`). Full mode: centred both horizontally and vertically in the space above the now-playing section; edge to edge (`100vw`), capped at 600 px (only reached on desktop/tablet), and on short or landscape screens capped by that space minus 20 px above and below. Mini mode: left-anchored, as tall as every row of the section, controls included (`5.125rem + 90px`, 172 px). While the cover for the current `folder` is unknown (probing, or before the first snapshot) the square is empty, showing only the background; then the cover, or the placeholder (`src/assets/no-cover.png`) when there is none. No `folder` (offline, no song, streams, no `--music-url`) shows the placeholder.
  - **Probing (`cover.ts`):** for a new folder, all of `cover.{jpg,JPG,png,PNG,jpeg,JPEG}` (the mirror is case-sensitive) load in parallel as `Image`s, so a miss costs one round trip instead of up to six; the first in that order that loads and decodes wins. Decoding before display makes the cover paint at once. Runs after the state is rendered, so title and controls never wait on it.
  - **No flicker:** results, hits and misses, are kept per folder URL for the session; a track change within the same folder changes nothing, and returning to a folder shows its cover or placeholder in the same frame as the title. So a cover added to the mirror (or a probe that failed on a network error) is only retried after a reload. A result for a folder that is no longer current is still kept but not shown.
- **Marquee (`marquee.tsx`):** the reusable component for every one-line text that may not fit. Too-wide text waits 1 s, scrolls (50 px/s) until its end is visible, waits 1 s, scrolls back, and repeats (bouncing, not wrapping). One Web Animations API `translateX` animation on an inline-block span, so it runs on the compositor; distance and duration are recomputed by a `ResizeObserver` (rotation, the web font replacing the fallback). Text that fits does not animate. A text change restarts from the beginning.
- **Title:** `title`, or a placeholder when `null`, in a fixed-height marquee line.
- **Artist:** below the title, smaller and muted, same fixed-height marquee line; the album artist when the song has no artist (server-side); empty (height kept) when both are missing.
- **Album:** below the artist, smaller still (13 px, the size of the time) and muted, same fixed-height marquee line; the folder name when the song has no album (server-side); empty (height kept) when `null`. Spans the full row width (the chevron is beside title and artist only). Added without growing the section: the time moved onto the bar's row, freeing its line.
- **Progress:** the pure `position(snapshot, now)` (`progress.ts`, Vitest) computes the displayed seconds. A `requestAnimationFrame` loop runs only while playing and writes the bar (`transform: scaleX`) and the `m:ss / m:ss` text directly through refs, the text only when it changes, so Preact does not re-render per frame. `duration` `null` (streams): empty bar, elapsed text only.
  - **Seeking:** enabled in full mode while playing or paused with a known `duration`; otherwise `aria-disabled` and inert. Pointer events with capture on a 44 px tall box around the bar (spilling into the gaps above and below its 1rem row; `touch-action: none` only while enabled), like the volume slider. Pointer down and every move set the shown position from the x position, bar and time included, and thicken the bar (4 → 8 px); release sends one `seek`, cancel sends nothing. Switching to mini mid-drag cancels it. Keyboard: `role="slider"`, arrows ±5 s.
  - **Drag tip:** while dragging, a small bordered box shows the position as a percentage of the song, following the pointer (kept within the bar's ends). It sits exactly over the album line, above the finger, so no text peeks out around it.
  - **No jump back:** after a seek the sent position is shown, advancing while playing, until the next state push or at most 1 s (MPD rejected it).
  - **Time beside the bar:** one 1rem row, the bar (`flex: 1`) vertically centred, the time right-aligned at the row's end. Its box has a fixed width, set by an invisible sizer text in the same grid cell (`timeSizer` in `app.tsx`): `00:00 / 00:00` (90 px), which fits every time under an hour (digits are tabular), and also any stream's elapsed time; `0:00:00 / 0:00:00` from a 1 h duration, `00:00:00 / 00:00:00` from 10 h. So ticking never changes the bar's length; only a song of an hour or more widens the box. Bar: 248 px in full mode at 390 px; 60 px in mini (45 at 375), the cost of the time sharing the narrow column.
- **Layout:** single column for iPhone portrait; `.app` is a full-height (`--app-height`, see below) flex column: the queue area (`flex: 1`) above the now-playing section, so progress bar and controls stay at fixed positions at the bottom. Touch targets ≥ 44 px tall, safe-area padding, colours from the CSS variables.
- **Fixed viewport:** the document never scrolls or zooms: `html`/`body` have `overflow: hidden`, `overscroll-behavior: none` (no rubber-band bounce in iOS Safari ≥ 16, no overscroll stretch or pull-to-refresh in Chrome) and `touch-action: pan-x pan-y` (no pinch or double-tap zoom; a descendant's effective `touch-action` is intersected with its ancestors', so it covers the whole page). iOS Safari (since iOS 10) ignores `user-scalable=no` and `maximum-scale` for pinch zoom, so the viewport meta doesn't set them. Lists that scroll (the queue) must be their own scroll containers. Future text inputs need `font-size` ≥ 16 px, or iOS zooms in on focus.
- **No selection:** `user-select: none` (plus `-webkit-` for Safari) on `:root`; descendants inherit it, so no text or image can be selected by drag, double-click or select-all (desktop). Future text inputs need `user-select: text`.
- **Screen stays on (`wake.ts`):** a Screen Wake Lock is held while the page is visible, so an idle phone doesn't dim and lock with the app open. The system releases it when the page is hidden; it's requested again on `visibilitychange` to visible, and a refused request is retried on the next touch. Needs a secure context (HTTPS or localhost); iOS Safari 16.4+, home-screen apps only since iOS 18.4 (WebKit bug 254545).
- **Full height (`--app-height`):** `100dvh`, except in iOS home-screen apps, where `100dvh`, `100svh`, `innerHeight` and percentage heights come out short by `safe-area-inset-top` (WebKit bug 254868), leaving an empty band at the bottom; there it is `100vh`, the full screen since there is no toolbar. An inline script in `index.html` adds `.standalone` to `<html>` when `navigator.standalone` is true, before first paint (`@media (display-mode: standalone)` is unreliable on iOS). For the same reason `html`/`body` have no `height: 100%` and no `position: fixed`: a fixed root is sized to the short viewport and clips the bottom of `.app`. Measured on an iPhone screenshot (402×874 pt): with `100dvh`, `.app` ended at ~812 pt, 62 pt (the top inset) short.
- **Modes:** the now-playing section is a grid with the same rows (title, artist, album, progress, controls) and the same height in both modes. Full mode positions the art absolutely against `.app`, in the band between the safe-area top and the section (whose height is fixed: `5.125rem + 138px`, so CSS can compute the band); mini mode puts it in a left column spanning every row, and all rows move right of it (the bar keeps its right end). So the queue area has one geometry in both modes and never reflows on a switch; it is only faded in (mini) or out (full, then `visibility: hidden`).
  - **Chevron (`.switch`):** at the top right of the mini box (beside title/artist) in both modes, so it never moves; the title and artist lines always leave room for it. Points down in full mode, up in mini (rotated). Not persisted: the app always opens in full mode (user decision).
  - **Animation (FLIP, `useFlip` in `app.tsx`):** on a click, every `[data-flip]` element's drawn rect is recorded, the layout switches in one render, and each element animates (Web Animations API, 350 ms, `cubic-bezier(0.4, 0, 0.2, 1)`) from the old rect to the new with `transform` only, so it runs on the compositor. Art and bar also scale (`data-flip="scale"`; the art is square in both modes, so uniformly); title, artist, album, time and the transport buttons only translate, so text and icons never stretch. The queue area's fade and chevron rotation are CSS transitions with the same duration and curve. Rects are recorded before cancelling running animations, so a click mid-switch reverses from the drawn position. `prefers-reduced-motion: reduce`: instant switch.
  - **Mode toggles** stay in place and only fade: out in 80 ms, before the sliding transport reaches them; in after 250 ms, once it has left (375 px is the tight case).
  - **No overflow:** going to full mode, the full-width rows start at their mini offset, past the right edge; `.app` has `overflow: clip` (no scroll container), which stops desktop browsers from flashing a horizontal scrollbar.
- **Font:** Iosevka Aile everywhere, Regular (400) and SemiBold (600, title). The woff2 files come from the upstream `PkgWebFont-IosevkaAile` release (nixpkgs has only TTF/TTC builds; converting those or building Iosevka from source were the alternatives), fetched by the flake and bundled by Vite under hashed `assets/` names, so they are cached immutably after the first load (~1.6 MB per weight, unsubset). `font-display: swap`; the fixed line heights keep the swap from moving anything.
