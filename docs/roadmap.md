# Roadmap

Work proceeds bottom-up in small steps, each usable on its own. Design details live in `architecture.md`.

## Current state

Now playing is done, including seeking on the bar in full mode. The queue area above it (mini mode) has the empty toolbar and the virtual list, sized to the queue and scrollable, its rows (track number, title, artist · album, duration) loaded on demand while shown, two lists ahead on each side, with a separator at each album change and the album's cover on its first row (probed two lists ahead, also while scrolling); it centres on the current song when opened and on each song change (paused for 15 s after the user scrolls), highlights it, keeps the visible rows' old text across a queue change until their refetch lands, and plays a row when tapped. There are no stored playlists.

- **Foundation:** Nix flake (dev shell, build, fmt, check, NixOS module); `lyrica-mpd` with the commands now playing needs; server bridging WebSocket clients to MPD (idle and command connections, reconnect with backoff, offline state); frontend embedded in the binary.
- **Now playing:** title, artist (album artist as fallback), album, album art from the HTTP mirror, smooth progress bar with the time beside it, tap / drag seeking on the bar (full mode), previous / play-pause / next, random / single / repeat, MPD volume slider, bouncing marquee for long lines, fixed-height layout pinned to the bottom, animated full / mini mode switch.
- **Play here:** plays MPD's `httpd` stream in the browser, with title, artist, album and cover on the lock screen.
- **iOS fit:** fixed viewport (no bounce, no zoom, no selection), full height in home-screen apps, safe areas.
- **Dark only:** gruvbox dark with its accent colours, regardless of the system setting.
- **PWA:** app icon and favicon, screen kept on while visible, portrait on Android.

## Next phases (in order)

Each item is one self-contained step. Order within a phase is the intended build order.

### Live queue

Read-only: no reordering, adding, removing or consume mode. The only way the queue changes from lyrica is loading a stored playlist (next phase). Design: `architecture.md` → "Queue" (server) and "Live queue" (frontend).

**Hard requirement:** the queue must not make anything slower. Now-playing updates, controls, the mode switch and scrolling stay as fast as they are now. Every queue operation, server and client, runs in the background, on demand and in small pieces; every step checks this in headless Chromium against the real queue: after MPD's own `idle` event, lyrica adds at most ~2–3 ms until the DOM changes, while the list loads and scrolls (measured from the event because `next` takes MPD 3–237 ms to open the next file); `mpc` pause/play within 2–4 ms end to end; no long tasks during a fling; no dropped frames in the mode switch.

1. **Queue reads in `lyrica-mpd`** — done. `Status` has the queue version, length, current position and id; `queue_range` (`playlistinfo START:END`) returns `Song`s with position, id, title, artist, album artist, album, track, duration and file; `play_id`. Every `Client` re-arms `TCP_QUICKACK` before each read: 100-entry windows in 0.43 ms median instead of 41 ms for most (`architecture.md` → "Queue measurements").
2. **Queue fields in the state message** — done. Version, length, current position and id (`queue` object, `null` offline); the idle loop also waits on the queue subsystem (`playlist`); the frontend's `Snapshot` type has the field, nothing renders it yet. Headless Chromium, `mpc` to DOM against the previous build, alternating: pause / play 1.5–2.3 ms either way; for `next`, MPD's own `idle` event comes 3–237 ms after the command (opening the next file), and the DOM changes 1.0–2.3 ms after it, one outlier of 12.8 ms in 32 (before: 1.1–2.3 ms in 32).
3. **Queue windows over the WS** — done. A third MPD connection serves window requests from all clients (`{"type":"queue","version","start","end"}` → `{"type":"queue","version","start","songs"}`), capped at 200 entries, `[]` when MPD rejects the range, `null` when not served; the WS loop hands requests off without awaiting and prefers state pushes over window replies; `TCP_NODELAY` on accepted HTTP / WS connections. Server only: the frontend ignores `queue` messages until the list uses them. Tested with the fake MPD: a stalled window read never delays a state push or a command on the same WS connection. Against the real MPD, with a separate client fetching windows back to back (~2000/s, two in flight), lyrica adds 1.2–2.3 ms after MPD's `idle` event to the DOM (unloaded: 0.2–1.2 ms); most of the increase is MPD contention, the same load sent straight to MPD costs nearly as much (`architecture.md` → "Queue measurements").
4. **Mini layout** — done. The queue area (`.queue`) is a flex column: the toolbar (`.toolbar`, empty, 44 px, `flex: none`) above the list's scroll container (`.queue-list`, `flex: 1`, `min-height: 0`, `overflow-y: auto`, `overscroll-behavior: contain`), empty until the virtual list; the "Queue" placeholder text is gone. Geometry identical in both modes and to the previous build; injected rows scroll inside the list, never the page; mode switches unchanged (no long tasks); pause / play unchanged (`architecture.md` → "Queue layout").
5. **Virtual list** — done. `queue.tsx` renders the list over a bounded scroll space (18,000 rows of 56 px) mapped onto the queue through an anchor, re-anchored when scrolling stops and the viewport has left the space's middle half, so the queue length has no height limit; a recycled pool of the rows in view ± 15; every row empty (nothing loads until step 6); opens at the top. Only the queue length goes in, via a `useMemo`'d element, so state pushes don't re-render it. The arithmetic is in `virtual.ts`, with Vitest tests at the boundaries. Against the real queue (175,872): pool constant (42 rows at 390×844, 39 at 375×667), viewport covered at every frame of six flings, re-anchors leave the screen unchanged and wait for a held touch, both queue ends reachable and flush, no list mutation from state pushes, no long tasks; mode switches and pause / play unchanged (`architecture.md` → "Virtual list").
6. **On-demand loading** — done. A `QueueStore` (`queue-store.ts`) fed by `ws.ts` (`connect(onSnapshot, onConfig, store)`: socket opens, each snapshot's `queue`, parsed `queue` replies), outside `App`'s state; the list reports its visible rows on every scroll pass and re-renders at most once per animation frame when a stored block overlaps its rendered rows. Blocks of 100, one request each, only while mini mode is on and the page visible: the visible ones first, then up to one viewport beyond, nearest first (ties below), at most two in flight; kept within ± 1,000 rows of the view; old-version replies dropped; `[]` not retried, `null` retried after 1 s; a new version or offline drops every block; a socket open frees in-flight slots. Rows show title, artist · album and duration (layout to iterate on). Vitest covers the store's order, clamping, limit, reply kinds, version change, eviction, offline, reopen and hiding. Against the real queue: rows filled 45 ms after switching to mini and matching `playlistinfo`; no request in full mode; flings filled within 0.3 ms of each stop, at most two outstanding even with replies delayed 100 ms, no long tasks; far-and-back, visibility reconnect mid-load and offline / reconnect all refill; state pushes don't touch the list; mode switches unchanged; pause / play within 0.34–1.47 ms after the idle event while scrolling and loading (`architecture.md` → "On-demand loading").
7. **Auto-centre and highlight** — done. `centre()` in `virtual.ts` places the current row mid-viewport (flush at the queue's ends). The current song reaches the list through the store (`store.current`, a `current` notification from `state`, handled in the list's animation-frame pass), so a song change renders now playing first and the list in the next frame; `App` calls `show` in a layout effect and `show(true)` notifies `opening` before planning, so every switch to mini centres before the fade-in's first frame and requests the current song's block first. Touch, wheel, mouse `pointerdown` and `keydown` on the list pause centring for 15 s after the last scroll event or touch end (longer while a touch is held); programmatic scrolls don't. The row with the current `id` is bright orange (`#fe8019`). Vitest: `centre()`, store `current` and `opening`. Headless Chromium against the real queue, compared with the previous build: opening paints its first frame already centred (row centre within 0 px), rows filled by the second frame, the current song's block requested first; after `mpc next` (10, random) the list moves in the frame after the title, highlighted and filled 38–48 ms after it (one block fetch); pausing and resuming as specified (re-centred 15.0 s after the last scroll, 15.0 s after a 17.9 s held touch ended); full mode neither scrolls nor requests; a reconnect re-centres; title, pause / play, fling and mode-switch timings unchanged (`architecture.md` → "Auto-centre measurements").
8. **Auto-update** — done. Store blocks carry their queue version; a new version keeps the blocks overlapping the visible rows as old rows, shown until their current-version replacement arrives (no blank flash), and drops every other block, marker and retry; only current-version blocks count as held, so the visible old ones are refetched first; rows past the new length go at once; position-stable (the viewport's top keeps its queue position; the current song re-centres while auto-centring). The list itself is unchanged. Vitest (store): old entries kept and replaced in place, the rest dropped, `[]` / `null` on a refetch, several versions in a row, entries past the new length gone, old blocks evicted by distance. Against a throwaway MPD (`development.md` → "Throwaway MPD") with a 175,000-entry queue, every frame recorded: appending, deleting above the view and in view (centred and paused) and from the view to the end left no filled row blank in any frame (the previous build blanked every visible row for a frame), refetched only the visible blocks and showed the new text within two frames of each reply; moving the current song, shuffling and replacing the queue filled the new view within two frames of the replies; full mode requested nothing. Hard-requirement timings on the real MPD unchanged (`architecture.md` → "Auto-update measurements").
9. **Album grouping** — done. Adjacent entries with the same album (and folder) form a group; group-start rows get a 1 px separator line at their top (`::before`, no reflow), every row a track-number column on the left; row heights unchanged (`architecture.md` → "Album grouping"). Each request starts one entry before its block, so every block decides its own group starts (`store.starts(position)`), whatever is loaded around it or its version. Vitest (store): requests and replies with the leading entry (block 0 has none; the leading entry is never served), group starts within a block and at its first row, `album` `null` and folder changes, an old block after a version change keeping its own starts, `undefined` when not loaded or past the length. Headless Chromium against the real queue with `--music-url`, compared with the previous build: separators and track numbers matched `playlistinfo` on all 378 rows checked (9 spots, block starts included); each separator appeared in the same frame as its row's text; row rects unchanged, every title at the same x; four-digit track numbers stay inside the row; flings, title, pause / play and mode-switch timings unchanged (`architecture.md` → "Album grouping measurements"). Screenshots at 390×844 and 375×667.
10. **Lazy cover art per group** — done. The group-start row shows its group's cover (40 px square) in the left column, widened from 24 to 40 px, instead of its track number; the other rows keep their track numbers, and so does the first row when the folder has no cover (no placeholder) or until it's found (`architecture.md` → "Cover per group"). Probed through `cover.ts`, which now shares in-flight probes, only for the visible group starts once the list has settled (150 ms without scrolling, no touch held), then on each scroll pass while settled; a found cover marks the list stale for its next animation frame; nothing in full mode. No Vitest (DOM timing). Headless Chromium against the real queue with `--music-url`, compared with the previous build: at 20 spots every visible group start matched a direct probe of its folder; probes 150–151 ms after the last scroll, none during flings, each folder once; per frame (after layout) no wrong, early or unloaded cover; a 13.6 MB cover in view during drags caused no long tasks and no change in frame gaps; full mode and no `--music-url` probe nothing for the list; row rects unchanged, titles at x = 72 px, four-digit track numbers inside the column; pause / play and mode-switch timings unchanged (`architecture.md` → "Cover measurements"). Screenshots at 390×844 and 375×667.
11. **Tap to play** — done. Tapping a loaded row sends `{"type":"playid","id"}` with its entry id (`Command::PlayId` → `Client::play_id`); now playing and the highlight follow the state push. One delegated `click` listener on the list, so scrolls and fling-stopping touches never play. Tapping the current row sends nothing. The tap resumes auto-centring, so the push's song change centres the tapped row (the current row centres at once). No press style; tap highlight transparent on the list (`architecture.md` → "Tap to play"). Rust: `playid` parsing (valid id; negative, fractional and missing rejected), dropped while offline. Headless Chromium against the real queue, compared with the previous build: taps on cover and track-number rows at the top, middle and bottom of the list played the tapped row's id and the highlight appeared centred in the push's frame; tap to state push 16–42 ms; swipes and fling-stopping taps sent nothing; the current row and unloaded rows sent nothing; after a tap `mpc next` centred at once; a mouse click played. Against a throwaway MPD, a deleted song's stale row logged MPD's `No such song` and moved nothing. Pause / play, fling and mode-switch timings unchanged (`architecture.md` → "Tap measurements"). Screenshot at 390×844.
12. **Covers ahead of the view** — done. The list probes the covers of the group starts within two list heights above and below the view (five screens), not only the visible ones, and the store's wanted blocks widen from one viewport to two on each side (`AHEAD_VIEWPORTS`) so their folders are known; probing runs on every animation-frame pass, also while scrolling, without the 150 ms settle wait, except while the list moves faster than 100 rows/s (`AHEAD_ROWS_PER_S`, over the last 100 ms), resuming in the first slower pass or 50 ms after the last one (stopped); at most 12 list probes in flight, visible first, then nearest first on the scroll's side (`architecture.md` → "Ahead of the view"). Vitest (store): wanted blocks span two viewports on each side, visible first, nearest first, ties below. Headless Chromium against the real queue with `--music-url`, compared with the previous build: scrolls of 10–90 px per frame and touch flings showed every found cover in the first frame its row was visible (previous build: 0–1 per run, the rest popped in after the stop or never showed); none probed at 1,000 px per frame, probes 67 ms after its stop, visible first, then the scroll's side; never more than 12 in flight; opening probed 7–18 ms after the click and kept every fade-in frame; 2–14 probes (0.2–10 MB) per stop in typical regions, 41–44 (all misses) in a region of a folder per row; no long tasks, fling frame gaps, pause / play and mode-switch timings unchanged (`architecture.md` → "Ahead measurements").
13. **Background preloading (conditional):** in full mode, keep the blocks around the current song loaded and current, and their covers probed, at idle priority, so switching to mini shows a filled list at once. Kept only if the hard-requirement checks show no measurable impact; otherwise removed.

### Stored playlists

A button in the mini-mode toolbar opens the list; there is no general settings menu. Listings go over the queue connection.

1. **Playlist protocol in `lyrica-mpd`:** `listplaylists`, `clear`, `load`.
2. **Playlists over the WS:** list request and reply; a load command that clears the queue and loads the playlist.
3. **Playlists button and list:** a toolbar button opens a list of stored playlists; tapping one replaces the queue.

## Deferred phone checks

Checks headless Chromium can't make, to do on an iPhone (home-screen app) before the live queue counts as finished:

- **Album grouping (step 9):** the separator is visible but subtle.
- **Lazy cover art (step 10):** flinging past big covers (13–14 MB near positions 137,507 and 137,526) doesn't stutter.
- **Tap to play (step 11):** a tap plays the row; a tap that stops a fling doesn't; no grey tap flash; the scroll indicator stays hidden; the song-change jump and the fade-in's first frame look right.
- **Covers ahead of the view (step 12):** covers are already showing as rows scroll into view during ordinary drags and flings, and during a hard fling's tail and after it stops; no stutter while they load. If they still pop in after hard flings, raise `AHEAD_ROWS_PER_S` (100 rows/s; headless touch flings peak at 67–105 rows/s, so the iOS speeds are unmeasured).
